    function stableStringify(value: unknown): string {
  if (value === null || typeof value !== 'object') return JSON.stringify(value) ?? 'null';
  if (Array.isArray(value)) return `[${value.map(stableStringify).join(',')}]`;
  const obj = value as Record<string, unknown>;

核心发现

四条结论，按影响排序
01
同步链的「水位」是单列游标，不是严格游标。

pull() 用 updated_at=gt.{since} 翻页，而 buildPushPayload() 在同一循环内多次取 Date.now()，同毫秒写入在超过一页（500 条）时会被 gt 跳过且永不回补。这是全项目唯一会「静默丢数据」的路径，优先修。

02
账本访问控制的唯一凭据是公开常量。

RLS 策略比对 x-ledger-key 请求头，而这个值来自 syncDefaults.ts，会随 Vite 构建打进 dist/assets/*.js。任何人打开站点源码即获得「读全账本 / 删全账本」的完整权限。文档已承认其非秘密，但没有替代鉴权手段。

03
场次快照会与实时账目分叉。

voidOrder() / restoreOrder() 只改订单，不重算 session.summary，而 refreshSessionSummary() 在 src/ 内没有任何调用点。本地页面临时用 sessionReport() 重新算，看板不露馅；但同步与合并会把过期的 summary 传播到另一台设备。

04
写路径的读放大是下一个性能天花板。

useLiveQuery(() => loadAll()) 订阅了全部 7 张表，任何一次开单都会重读全库并重放 fifoAllocate()。以每场 60 单估算，两千单后单次开单的派生计算已到数十毫秒量级，且随历史线性增长。
