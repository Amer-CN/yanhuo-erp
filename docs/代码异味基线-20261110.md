### 关键取舍

1. **H-003 只重算已结账场次**：open 场次的报表本来就由 `sessionReport` 实时算，写快照会凭空造出 `summary`，还会让下游误以为该场已结算。
2. **H-004 判据用 FIFO 剩余量，不用「有没有明细引用」**：赠品也消耗批次，只看明细存在会漏判；`remaining < qtyBase` 才等价于「这批货已经被卖掉/送出过」。批次不存在时保持原行为（直接删 + 入队 delete），不新增错误分支。
3. **H-002 的升级兼容用 `gte`**：没有 id 水位时按 `updated_at=gte.{ts}` 重放该毫秒。用 `gt` 会在升级瞬间延续旧 bug，丢一轮数据；重复应用是幂等的，代价只是一次多拉。

1. **协议改动必须同步改假 Supabase**：`scripts/mock-supabase.mjs` 原先只解析 `updated_at=gt.`，不认 `or=`。只改客户端会让 e2e 每页都从 0 重放、"假通过"。本批已让 mock 支持复合游标与单列 `gt`/`gte`（顺带可模拟灰度混跑）。

### 关键实现要点

1. **清空是绝对操作，不能只靠水位传播**（第 1 条）。`clearCloud()` 仍是 PATCH 软删除（保留 H-005 / 第十四节的「可恢复、不可物理抹除」），但随后 upsert 一条标记行：id 为 `__ledger_cleared__:<ledger>`（带账本码，多账本共用一张表时不互相覆盖），`kind = 'ledger'`，值取本次 `Date.now()`。`pull()` 起始游标改 `resolvePullStart()`：读到标记值与本地 `yh-sync-cleared-at` 不同，就把 `lastPull / lastPullId` 归 0 做**一次幂等全量重放**；标记值**先落盘再开拉**，中途失败也不会反复重置、卡在同一份重放上。标记行在 `pull` 侧整行过滤，既不写业务表也不进未知 kind 诊断；`readClearMark()` 任何异常都返回 0，**绝不阻断同步，更不能阻断开单**（本地优先红线）。
2. **两侧降级必须对称**（第 2 条）。推送侧早有 `recordColumnMissing`，拉取侧原先没有；一旦远端没重跑 `schema.sql`，`select=...record_updated_at...` 会让每页都 400，同步链整体挂死。新增 `PULL_COLUMNS_LEGACY` 与 `pullRecordColumnMissing()`：只有错误文本**明确指向 `record_updated_at`** 且带 `PGRST204 / 42703 / does not exist / schema cache` 才降级重试一次，避免把网络错误误判成缺列；已降级仍报错则按真实错误上抛。诊断写 `yh-sync-warn`，复用推送侧 `warnDegraded()`（隐私模式下 localStorage 抛错被吞掉）。
3. **失败提示必须出现在用户当前看得见的那一层**（第 3 条）。`delError` 由 `string` 改为 `{ batchId, message }`，提示渲染在删除确认 Sheet 内该批次条目下方并带 `role="alert"`；三处清除（打开确认框、关闭 Sheet、删除成功）保证不会串到下一个批次。
4. **单商品口径与原全表口径等价**（第 4 条）。`fifoAllocate` 内部按 `productId` 独立排队（`byProduct` / `queueIdx` / 兜底均价都按商品分组），所以 `loadProductLedger(productId)`（批次 + 该商品明细 + 明细所属订单，脏引用已过滤）算出的 `batchRemaining` 与三张全表重放一致，代价从 O(全库明细) 降到 O(该商品明细)。批次不存在时保持原行为（直接删 + 入队 delete），不新增错误分支。
5. **补录进货只有三种情形会改写历史成本**（第 5 条）：① 新批次插进 FIFO 队列中间（`fifoReordered`）；② 变动前该商品已超卖；③ 变动后开始超卖。`batchSortKey()` / `isFifoLast()` 与 `calc.fifoAllocate` 的排序键（到货日 → 创建时间 → id）保持同口径，用于判断是否队尾追加。队尾追加且前后都不超卖时直接短路，避免每次进货都重写快照、抖动 `updatedAt` 与发件箱。命中时一次读全表 + 一次 FIFO 重放供所有受影响场次复用，与 `migrateSessions` 同口径。
6. **快照重算一律 best-effort**（第 7 条）。新增 `bestEffortSnapshot(label, run)`（`try/catch` + `console.warn`），`createBatch` / `deleteBatch` / `voidOrder` / `restoreOrder` 全部走该包装：主数据（进货、作废）已落库入队，不能因为补偿重算失败把它报成失败（否则用户会重录一条）。`HistoryPage` 两处裸 `await` 补 `try/catch`，分别提示「作废失败，请重试」「恢复失败，请重试」。
7. **索引替换顺序不可颠倒**（第 8 条）。先 `create index if not exists yh_records_ledger_updated_id`，再 `drop index if exists public.yh_records_ledger_updated`；两条都幂等，注释里给出查询侧覆盖证据（三列索引对 `(ledger, updated_at)` 前缀查询完全覆盖）与回滚语句。`drop index` 会短暂持表级排他锁，本表规模极小，注释已说明零锁可用 `drop index concurrently`（不能在事务块内执行）。

### 误报证明（第 6 条：删除批次是否改变 uncovered 成本）

**结论：误报。** 证明分两步：

1. **能删的批次一定没被扣过**：`deleteBatch()` 的门槛是 `remaining < qtyBase` 即拒绝，能走到删除就说明 `remaining === qtyBase`（批次从未被任何明细消耗）。既然没有任何 `lineCost` 指向它，删除它不影响任何一条明细的成本。
2. **兜底均价不参与该商品任何 `lineCost`**：兜底均价只在「该商品存在未覆盖明细（超卖）」时才会被写入 `lineCost`。而 `remaining === qtyBase` 意味着该商品总进货量 ≥ 已售量，不存在未覆盖明细；因此删除这个批次既不改 FIFO 扣批序列，也不改任何明细的成本来源。

**验证方式**：新增用例在删除前后各算一次，断言 `lineCost` 与 `session.summary` **完全相等**（不是「误差在阈值内」，是逐字段相等）。删除侧仍保留一次 best-effort 重算调用，只为兜住脏数据（如 `qtyBase ≤ 0` 的批次会参与兜底均价加权），正常数据下该调用在 `refreshClosedSummariesAfterBatchChange()` 里被短路，不产生写入。

### 顺带修正的既有缺陷

1. **`BATCH_IN_USE_MSG` 文案承诺了不存在的功能**：原文案「只能改数量」，但仓库里既没有 `updateBatch()`，进货页也没有编辑入口。现改为引导到「库存 → 修正库存（盘亏/盘盈）」，即用户当下真能执行的动作。
2. **`PurchasePage` 的 `delError` 未随批次切换清理**：改为带 `batchId` 的结构后，提示只对失败的那个批次显示，同时打开确认框 / 关闭 / 删除成功三处清除。
