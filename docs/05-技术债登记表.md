## 0. 执行摘要

系统整体健康度**好于同规模自用项目**：类型严格（`strict`、零 `any`、零 `@ts-ignore`）、核心金额/FIFO/场次计算有 23 个单测用例、离线优先与同步链路有 8 个 E2E 脚本、性能有量化基线（LCP 1724ms → 1232ms）、设计与交接文档完备。

真正的风险集中在 **「账本是唯一资产」这条主线**，而不是代码风格：

| 排序 | 问题 | 为什么现在就要处理 |
|---|---|---|
| 1 | 云同步凭据内置在公开前端包中（TD-01） | 仓库与 Pages 站均公开，账本隔离仅靠一个随包发布的共享密钥；泄露即全量读写 |
| 2 | 数据迁移/清缓存无自动备份兜底（TD-07、TD-08） | 唯一不可再生资产；iOS 清存储、换机、升级失败均可能不可逆丢账 |
| 3 | 写入/同步/合并路径零单测，E2E 未进 CI（TD-03、TD-04） | 风险最高的代码恰好没有自动门禁，全靠人肉跑脚本 |
| 4 | 同步为「新时间戳覆盖」（TD-02） | 两台手机同时改同一单会静默丢改动，且无法复盘 |
| 5 | v1/v2 双记账路径并存（TD-06） | 两条写入路径都能落库，认知负担与回归面翻倍 |

**结论**：按「真机摊位试用（M6）」这个最近的业务节点，先做 **6 个 P0/P1 项**（约 8–11 人日）即可把「丢账/被改写」的尾部风险压到可接受；其余进入季度节奏，不必停业重构。

### TD-01 云同步凭据内置 + 账本隔离依赖随包共享的密钥

| 字段 | 内容 |
|---|---|
| 维度 | 安全 / 数据完整性 |
| 严重度 | **Critical** |
| 优先级 | P0 |
| 工作量 | M（3–5 人日） |
| 类型 | 战略性（零配置是明确取舍），但**补偿控制缺失 → 处于未管理状态** |
| 证据 | `src/db/syncDefaults.ts:6-9`（内置 URL + publishable key + `ledgerKey`）；`supabase/schema.sql:24-38`（RLS 用 `x-ledger-key` 请求头做账本隔离）；`docs/03-云同步设置.md`；README 公开线上地址与仓库 |

**问题**：`ledgerKey` 被当作「半秘密」使用——它同时是 RLS 的过滤条件，又被编进公开的前端产物。任何打开线上站点的人都能从 bundle 中取出 `url/anonKey/ledgerKey`，直接对 `yh_records` 做全量 `select/insert/update/delete`。`schema.sql` 注释中还提供了「退回 `using(true)`」的应急方案，一旦执行即彻底开放。

**影响**：账本内容（品名、进价、售价、毛利、设备名）可被读取或篡改；恶意写入会通过同步污染两台手机。对自用摊位的现实威胁主要是「误开放 / 被爬取」，而非定向攻击——但后果不可逆。

**建议修复（分两步，先做 1）**
1. **止血（0.5 人日）**：轮换 `ledgerKey`；在 Supabase 侧确认 `yh_records` 仅授予 `anon` 必要权限；把「任何人拿到 key 可读写」写进 `docs/03`，并明确禁止启用 `using(true)` 回退方案；增加服务端 `updated_at` 合理性约束。
2. **根治（3–5 人日）**：改用 Supabase Auth 匿名登录 + `auth.uid()` 绑定账本成员表，RLS 基于 JWT 而非共享头；或拆为「每台设备一个 token」并支持吊销。

**验收**：用未持有 credential 的第三方会话请求 `yh_records` 返回空集/403；bundle 中不再出现可直接复用的账本凭据。

### TD-02 同步为「新时间戳覆盖」，无冲突检测、无退避重试

| 字段 | 内容 |
|---|---|
| 维度 | 可靠性 / 数据完整性 |
| 严重度 | **Major** |
| 优先级 | P1 |
| 工作量 | M（3–5 人日） |
| 类型 | 意外（简单优先的副产品） |
| 证据 | `src/db/sync.ts:221-245`（推送时 `updated_at: Date.now()`，`resolution=merge-duplicates`）；`src/db/sync.ts:318-370`（拉取按 `updatedAt` 覆盖本地）；`src/ui/useSync.ts:88-92`（固定 10s 轮询，失败只写 `lastSyncError`，无退避）；`src/db/outbox.ts`（发件箱按 `kind:recordId` 去重，仅保留最后状态） |

**问题**
- 推送成功即用**本地当前时间**覆盖远端 `updated_at`，即使远端记录更新——「后写赢」实际由**推送时刻**决定，而非业务修改时刻。
- 无版本向量/字段级合并；两机同时编辑同一单，后同步者静默覆盖。
- 失败仅记录错误字符串，下一次仍按 10s 固定间隔重试，无指数退避与抖动；真机弱网下会持续打点。
- `outbox` 每类记录只保留一条（`id = kind:recordId`），中间的编辑顺序不可追溯。

**影响**：静默丢改动，且事后无法还原；弱网时电量/流量浪费。对「两个人各记各的」大多数场景影响有限，但恰好在「同一笔单改价/改数量」时命中。

**建议修复**：推送携带 `recordUpdatedAt`（业务时间）而非 `Date.now()`；拉取按 `max(recordUpdatedAt)` 决策并记录冲突日志（同 id 双端不同 `updatedAt` 时保留双方快照，UI 提示「这单在两台手机都改过」）；失败改为 1s/2s/4s…上限 60s 的退避；把冲突事件写入本地 `conflicts` 表供人工核对。

**验收**：两设备交替编辑同一单的 E2E 用例能检出冲突并保留两份快照；断网 30 分钟后恢复，10 分钟内补发完成且不重复。

### TD-09 PWA 采用 `skipWaiting + clientsClaim`，更新会立即接管正在使用的页面

| 字段 | 内容 |
|---|---|
| 维度 | 可靠性 / 基础设施 |
| 严重度 | **Major** |
| 优先级 | P1 |
| 工作量 | S（0.5–1 人日） |
| 类型 | 战略性（autoUpdate 换取零运维），但未评估「开单中被打断」 |
| 证据 | `vite.config.ts:9`（`registerType: 'autoUpdate'`）；`dist/sw.js:1`（`self.skipWaiting()`、`s.clientsClaim()`、`cleanupOutdatedCaches()`） |

**问题**：`autoUpdate` + `skipWaiting/clientsClaim` 会在检测到新版本时自动调用 `updateServiceWorker(true)` 并 reload 页面。新建单据的草稿整体存在 `sessionStorage`（`recordDraft.ts:52-58`，仅 `mode === 'new'` 保存），reload 后可由 `RecordEditor.tsx:92` 恢复；但 `edit` / `patch` 模式不写草稿，正在编辑或补记的内容会丢失，弹层与焦点状态也会重置。

**影响**：摊位使用中被打断。`new` 模式可恢复草稿，`edit`/`patch` 模式会丢掉未提交的修改（需重新填写）；比「更新慢一天」严重。

**建议**：改为 `registerType: 'prompt'` + 顶部「有新版本，收摊后再更新」条；同时把 `saveDraft` 扩展到 `edit` / `patch`（以 `mode:orderId` 作 key），确保任何模式 reload 后可恢复。优先做 `prompt`。

**验收**：发布新版本时页面不会自动 reload；`edit`/`patch` 模式在 reload 后能恢复草稿；用户可自主选择更新时间。
