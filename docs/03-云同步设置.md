# 云同步设置（Supabase）

> 目标：**云端有一份主账，离线照常开单，联网自动推拉**。
> 本机始终是“可离线工作的副本”；手动导出/导入降级为备份手段。
>
> **本轮状态：本地整合、门禁与独立真实协议验收通过，生产/目标真机待人工执行。** 候选未部署，生产迁移未执行；真实 loopback PostgreSQL/PostgREST HTTP、多连接及条件重连丢响应重试已验证。本文描述候选协议与人工升级顺序；独立测试不能代替生产或两台目标手机，最终凭证见[总方案](superpowers/plans/2026-11-13-stability-repair.md#最终验收记录2026-11-15)，人工动作见[发布检查表](stability-closeout/RELEASE-CHECKLIST.md)。

## 零配置（默认，开箱即用）

应用已经内置了项目 URL、publishable key 和同步码。**两台手机打开同一个网址就自动是同一本账，不需要填任何东西**。

- 设置页会显示「配置：内置，打开即用」
- 想换自己的同步码：设置与同步 → 云同步 → 修改配置（两台手机都换）
- 注意：内置同步码会随公开仓库的前端代码发布，理论上懂技术的人翻代码能看到；如果在意隐私，请换成自己的同步码

下面的手工配置用于新建项目；已有账本先按第十四节 prepare → 两台升级 → finalize，不能把新库脚本直接当升级脚本。恢复/撤销合并后要走第七节的差异预览重连；切换账本或清云能力未就绪时，候选会拒绝相应操作并保留本机数据。

## 一、为什么需要 Supabase

GitHub Pages 只能放静态文件，存不了账。Supabase 提供免费的 Postgres 数据库 + REST 接口，正好当同步后端。两台手机共用同一个 Supabase 项目和一个同步码。

## 二、新建项目配置（已有账本先看第十四节）

1. 打开 <https://supabase.com>，用 GitHub 登录，`New project`：
   - 名称随意，数据库密码记一下（后面一般不用）
   - Region 选 **Singapore**（离国内近）
   - 等 1 分钟项目初始化
2. 维护者先在独立测试项目验证，再在新项目的 `SQL Editor` 执行[新库正本](../supabase/schema.sql)；新库直接建立 `(ledger,id)` 主键和协议对象。设置页“怎么配置？看步骤”的显示/复制也读取同一正本。已有账本不要清表重建，走第十四节迁移包。本轮没有授权执行生产 SQL。
3. 左侧 `Project Settings → API`：
   - 复制 **Project URL**（形如 `https://xxxx.supabase.co`）
   - 复制 **anon public key**
4. 手机打开烟花账 → `更多 → 设置与同步` → **云同步**：
   - 填 Project URL、anon key
   - 点「生成」得到一个同步码
   - 「保存并启用」
5. 第二台手机填**同样的 URL、anon key、同步码**，保存启用。

两台都显示「已连接」后，一台开单，另一台几秒到十几秒内会自动看到。

## 三、自动同步的时机

- 打开 App / 切回前台
- 网络从断开变连通
- 每成交一单（本地写完后约 0.7 秒推送）
- 每 10 秒拉取一次对方的新记录

本地写入永远先成功，网络只影响“什么时候同步出去”，不影响开单。

## 四、同步什么、不同步什么

| 数据 | 同步 | 规则 |
|---|---|---|
| 商品、进货批次、库存调整、场次 | 是 | 按记录身份和业务版本合并；本机待推送时保护本机改动 |
| 销售单/明细 | 是 | 订单含可编辑字段；按订单及完整明细核对，跨页明细暂存待父单/完整快照齐备；不能按“只增不改”理解 |
| 可同步设置（如临期天数） | 是 | 后写胜 |
| 设备名 / 设备 ID / 本机操作人 / 本机诊断 | 否 | 设备身份与恢复状态保留在本机 |

删除用“墓碑”记录（`deleted=true`）同步，另一端按协议处理对应记录。发件箱只确认实际发送的版本，网络回执不能顺带删除同 id 后续编辑。非法金额或不完整订单数据不会当作完整业务结果静默落库；排查诊断见第十二、十三节。

## 五、安全说明

- 自定义配置的 `anon key` 和同步码只存在手机本地（localStorage）；**内置配置**的 URL / publishable key / 同步码会随前端包公开，**不是秘密**（见第八节）。
- 数据库用 RLS 策略校验请求头 `x-ledger-key`：只有带着正确同步码的请求能读写对应账本。
- 不要退回 `using (true)` 策略：那等于允许任何持有 anon key 的客户端读写全部账本（`supabase/schema.sql` 末尾有警告）。
- 想换同步码：改两台手机的同步码即可；旧数据留在旧账本下，不会自动迁移。轮换步骤见第八节。

## 六、常见问题

| 现象 | 排查 |
|---|---|
| 保存后显示「同步出错」 | 先点「测试连接」；确认 SQL 执行过、URL/key 没抄错 |
| 401 / 403 | 多半是 RLS 策略没建好，或 key 不是 anon public key |
| 一直「待推送 N 条」 | 检查网络；Supabase 免费项目长时间不用会暂停，去控制台恢复 |
| 第二台看不到新单 | 确认两台同步码完全一致（大小写/空格）；点「立即同步」试 |
| 恢复后显示“已暂停，待确认” | 这是保护状态；按第七节“准备重连”，逐组核对，不要删除暂停标记或直接改 localStorage 强行启用 |
| 清云结果未知 / 本机还在 | 按第十一节重试同一 operationId；不得新建清空操作或手工抹掉本机数据 |
| 旧设备在清云后不能上传 | 核对当前 epoch、两台构建版本和 RPC 能力；先预览重连，不要改旧数据的 epoch 强行发送 |
| 数据想清空重来 | 两台先导出备份；区分只清本机/清云端。缺 RPC 或迁移未完成时拒绝清云，见第十一、十四节 |

## 七、和手动备份的关系

手动「导出备份 / 导入合并」保留，用于：

- 云端出问题时的兜底
- 换手机/重装时恢复
- 存一份到微信收藏

云同步正常时不需要再手动合并。

### 恢复与撤销合并后：先预览，再重新接入

恢复快照和“撤销合并”**只恢复本机，云端未回滚**。候选先隔离正在运行的同步，再原子替换本机业务数据、清旧 outbox/待决明细/旧诊断并持久暂停；页面重启仍保持暂停。它们不调用清云 RPC，也不以整库标脏把恢复快照覆盖到云端，其他设备独有数据应保留。

1. 核对恢复后的单数、完整明细和金额，再点“云同步 → 准备重连”。预览阶段只读取云端和本机差异，不上传、不发墓碑。
2. 订单和其明细作为一组。仅云端记录保留并带回本机；仅本机记录保留，确认后以新的业务时间 upsert；内容不同的每组都需明确选择本机/云端，不能默认全选本机。
3. 采用本机订单以该单完整明细为准：需为预览中该单云端多出的旧明细生成墓碑，避免旧 extra lines 重新出现。这是所选订单内的差异，不是清整本云账本。
4. 确认时必须重新核对本地状态、暂停代际、远端基线与 current epoch。上传还要求远端额外条件写 RPC 能力（`yh_reconcile_push`）及结果 receipt；服务端在同一事务中比较预览基线并写入，第三台在预览后的更新必须导致拒绝/重新预览，客户端二次 GET 本身不能关闭竞态。
5. 缺条件 RPC 能力、基线改变、数据不完整或预览过期时继续暂停并重新预览；“暂不接入”保持暂停。重连条件上传已由 `yh_reconcile_push` 实现；v2 能力响应不等于该 RPC 必然存在，缺失时明确暂停且不回退普通 POST。操作号、完整远端投影和首次发送内容在请求前持久保存，响应丢失后重试同一请求。

## 八、凭据公开性与轮换

### 公开性（重要）

- 应用内置的 `url`、`anonKey`（publishable key）和 `ledgerKey`（同步码）**都会被打进公开的前端产物**：仓库是公开的，GitHub Pages 上的 JS 也能直接下载。它们**不是秘密**，不能当密码用。
- `anonKey` 不是数据库管理员密钥，但配合 `ledgerKey` 已足够读写**本账本**的数据。

### 当前 RLS 的实际保证边界

- 能阻止：没有本账本 `ledgerKey` 的客户端访问本账本（跨账本隔离）。
- 不能阻止：任何拿到本账本 `ledgerKey` 的人读写本账本。账本隔离是「一本账一把钥匙」，不是「一把钥匙只给你」。
- 因此：不要把 `anonKey` 或同步码发到公开 issue、群聊、截图里；**不要**把 RLS 改成 `using (true)`（等于取消账本隔离，见 `supabase/schema.sql` 末尾警告）。

### 轮换步骤（对应执行计划 docs/06 §7-A；必须两台设备同时在场，先导出备份）

1. 在其中一台手机上：`更多 → 设置与同步 → 云同步`，先「导出备份」并确认文件能打开。
2. 确认另一台手机也在场、电量充足、能联网。
3. 两台手机分别打开「修改配置」，把同步码改成**同一串新的**随机值（建议 32 位以上），保存并启用。
4. 旧账本数据仍留在旧同步码下，不会自动迁移；确需迁移时，用备份导入新账本后再核对金额。
5. 轮换完成后，两台手机各开一单，确认能互相看到。

> 红线：轮换会让另一台手机立即失联，必须两台一起改；轮换前先备份。

## 九、升级到复合游标（2026-11，协议变更）

拉取水位从「单列 `updated_at`」改为「`(updated_at, id)` 复合游标」。

**为什么**：推送时同一批记录会取到相同的毫秒时间戳。旧实现用 `updated_at=gt.{since}` 翻页，一旦一页的首尾时间戳相同、同毫秒的记录又超过 500 条，剩下的会被**永久跳过**，且不会自愈。

### 升级步骤

三列索引与显式补列由第十四节迁移包统一处理；不要单建索引后就认定稳定性协议已升级。两台手机都应升级；仍用 `gt` 单列游标的旧端在“同毫秒超过一页”时可能漏记录。候选的协议还涉及主键与 epoch，必须按 prepare → 兼容前端 → 两端确认 → finalize 执行，不能套用旧版“新老端可长期混跑”的结论。PWA 更新由用户在收摊后确认，不会自动重载。

### 兼容说明

- 旧的 `localStorage['yh-sync-last-pull']`（时间水位）继续保留；新增 `localStorage['yh-sync-last-pull-id']` 保存游标 id。
- 老版本升级上来时没有 id 水位，首次拉取按 `updated_at=gte.{ts}` 重放该毫秒的记录：**不会因为升级丢一轮数据**，重复应用是幂等的。
- 清空同步配置（`clearSyncConfig`）会同时清掉两个水位键，以及第十二节提到的清空标记 `yh-sync-cleared-at`。
- 每日重放使用持久化续扫游标；首次下载或续扫未完成时继续显示未完成状态，不用一次成功请求冒充全账本已同步。迁移与索引以第十四节的现役脚本为准。

## 十、云端权限与能力协商

候选继续撤销 anon 的物理 `DELETE`，业务表只允许按 `x-ledger-key` 作用域读、增、改；策略为 `yh ledger read` / `yh ledger write` / `yh ledger update`，旧 `yh ledger access` 退役。撤销 DELETE 只阻止物理删除；持有同步码的人仍能软删或调用获准的清云 RPC，不能把它描述为“无法清空账本”。

- `yh_sync_capabilities` 按实际主键和账本状态报告协议、复合冲突目标、账本隔离、清云可用性、current epoch 与 `x-yh-clear-epoch` 要求；不能只凭某列/索引存在就宣告迁移完成。
- prepare 建立兼容对象但保留旧 `id` 主键；旧库尚未 finalize 时账本切换/清云不能按最终能力启用。新库正本直接使用 `(ledger,id)` 主键。
- `yh_ledger_state` 与 `yh_clear_operations` 不允许 anon 直接写；receipt 只可读本账本。清空和条件上传各自要求对应 RPC 能力，不能把“协议 v2 可用”误当所有后续能力已安装。
- 清云 RPC 采用最小 `SECURITY DEFINER`：固定 `search_path = pg_catalog, public`，账本仅由已校验的请求头取得，不接受任意 target ledger；内部显式限定 ledger，避免公开任意状态写 helper。普通读写仍由 RLS 限定。独立 loopback 双连接已验证清空与普通写共享同一账本锁顺序；不据此推断云供应商生产运维、连接池/代理拓扑或真实账号数据已验。

维护者的只读核对（先在独立测试库运行；本轮未执行生产 SQL）：

```sql
select polname, polcmd from pg_policy
where polrelid = 'public.yh_records'::regclass;

select grantee, privilege_type from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'yh_records'
  and grantee = 'anon' and privilege_type = 'DELETE';
```

预期有三条业务策略、没有旧 `for all`，anon DELETE 结果为空。函数定义/授权、receipt 隔离、清云回滚和旧 epoch 拒绝还需按[运维手册](08-运维手册.md#12-本轮候选的本地门禁与交付边界)分别做 SQL/RLS 与实际 HTTP 验证。不要用生产探测或开放 RLS 作为修复办法。

## 十一、事务清空与同操作重试

旧的“PATCH 全账本软删 + POST 标记行”两请求清云路径已从候选退役；它不能保证两步同成同败。候选仅在远端能力允许时调用 `yh_clear_ledger`，没有 RPC 或能力不符时拒绝清云，**本机数据保留**。

### 一次清空的合同

1. 客户端先把 operationId 与状态持久化到本机 `syncMeta`，再提交 RPC；提交前可取消，提交后确认/取消/Esc/遮罩/返回入口忙碌锁定，直到明确结果。
2. 服务端在一个事务内取得账本锁、推进 clear epoch、写业务墓碑、更新 `__ledger_cleared__:<账本>` 内部标记并写 receipt；任一失败整笔回滚。标记不计入业务记录或未知类型诊断。
3. RPC 从 `x-ledger-key` 取得账本，仅接收操作编号；同账本同 operationId 先返回原 receipt，不再次清数据。另一次清空必须是明确发起的新操作。
4. 客户端核对 receipt 的操作编号和结果并持久化，云端确认后才清本机。本机清空与该 operationId 的完成标记同事务提交；后续收尾失败重试时只完成剩余步骤，不再清掉后来新增的本机记录。
5. 清空后仍保持同步暂停。旧设备的缺失/过期 epoch 写入被拒，需预览重连；不能给旧 outbox 改 epoch 直接补发，否则会复活旧账本。

### `pending` / `unknown` / `confirmed`

| 状态 | 含义 | 操作 |
|---|---|---|
| pending | 已登记，尚未取得有效成功凭证；明确 4xx 仍需处理原因 | 保留数据和操作编号，修正环境后继续同一次 |
| unknown | 超时、断网或无效回执，服务端可能已提交 | 点“重试同一次清空”；禁止换新 operationId，禁止手工先清本机 |
| confirmed | 云端成功凭证已落本机，可能仍需完成本机清理 | 继续同一次，使用原 receipt，不再次清云端新单 |

如果重试后仍未知，先导出本机备份并向维护者提供操作编号、构建标识和错误；不要清缓存、删 `syncMeta` 或反复另起清空。receipt/current epoch 与状态持久化是恢复依据，不以“页面看起来空了”判定成功。

### 当前代际与权限

清云后，业务写入必须携带当前 `x-yh-clear-epoch` 和匹配的行 `clear_epoch`；缺头、错头、旧头或错误字段应拒绝。服务端写入与清空按同一账本锁顺序执行。PostgreSQL WASM 单会话只覆盖 SQL/RLS 语义；本轮已另用独立真实 PostgreSQL/PostgREST 验证 HTTP 头传递与多连接竞争，结果见总方案。生产与目标设备仍需人工验收。

## 十二、本地存储键清单（localStorage）

云同步的配置、展示和扫描水位使用 `localStorage`；**暂停/租约、恢复标记、协议能力、清云操作及重连基线使用 IndexedDB 的 `syncMeta`**。跨存储清理有恢复标记，重启会补完；不能只删 localStorage 就认定已重置。下面列出可供维护者只读诊断的本地键，不要用手改值绕过暂停或 epoch 检查。

| 键 | 用途 | `clearSyncConfig()` 是否清除 |
|---|---|---|
| `yh-sync-url` | Supabase 项目 URL（自定义配置才有；内置配置不写） | 否，关闭时保留配置 |
| `yh-sync-anon` | `anon` / publishable key | 否，关闭时保留配置 |
| `yh-sync-ledger` | 同步码，即 RLS 校验的 `x-ledger-key` | 否，关闭时保留配置 |
| `yh-sync-last-pull` | 拉取水位：`updated_at` 部分（毫秒） | 是 |
| `yh-sync-last-pull-id` | 拉取水位：同毫秒时的 id 部分（复合游标第二列） | 是 |
| `yh-sync-cleared-at` | 已观察的清空标记；不能替代 `syncMeta` 中的 current epoch / receipt | 是 |
| `yh-sync-last-replay` | 上次每日完整重放的本地日期 | 是 |
| `yh-sync-last-replay-cursor` | 每日全量重放的跨轮续扫游标 | 是 |
| `yh-sync-parent-lookup-after` | 待决明细补查父单的轮转位置 | 是 |
| `yh-sync-initial-pending` | 首次下载/续扫尚未完成 | 是 |
| `yh-sync-last-sync` | 上次同步成功的时间戳（设置页展示「已连接」） | 是 |
| `yh-sync-error` | 最近一次同步的错误文案，同步成功后清除 | 是 |
| `yh-sync-warn` | **新增**：诊断文案，可能是**多行**（换行分隔）。降级告警为单条；非法远端行为「拉取到非法数据已跳过：`kind`:`recordId`」，最多 20 条。只写不改；目前**不在界面上展示**，只能在控制台读 | 否 |
| `yh-sync-disabled` | 值为 `1` 表示停用云同步（E2E / 测试脚本用它避免写真实账本） | 置为 `1` |

补充说明：

- `clearSyncConfig()` 的用户动作是“关闭云同步”：持久暂停、保留连接配置并清扫描/展示水位，不是抹掉 `syncMeta` 中所有协议状态。
- 恢复/清本机操作会清旧队列、旧扫描状态和诊断，但保留完成恢复所需的控制信息；若提交后 localStorage 清理失败，恢复标记支持重启续做。
- `yh-sync-warn` 可在普通关闭时保留，恢复时清理；先处理告警原因再清诊断，不能用删告警代替迁移。
- 未知记录类型的诊断 `sync-unknown-kinds` **不是** localStorage 键，而是本地设置表里的一条记录（设备诊断，不上云）。
- 清云 operationId、状态和 receipt 在 `syncMeta` 中，页面会展示待确认操作；不要把它们贴到公开日志或手工删除。

## 十三、旧远端缺列的降级与告警

旧远端尚未显式补上 `record_updated_at` 时，新版拉取的显式列清单（`PULL_COLUMNS`）会遇到缺列；已有账本应执行第十四节 prepare，不能只重跑新库正本：

```
id,record_id,kind,data,updated_at,record_updated_at,deleted
```

PostgREST 遇到不存在的列会直接 400，整条同步链会被一次 400 打挂。所以拉取侧做了和推送侧对称的降级：

- **只在确认缺列时降级**：`pullRecordColumnMissing()` 要求错误文本里同时出现 `record_updated_at` 与 `PGRST204` / `42703` / `does not exist` / `schema cache` 之一，避免把网络抖动当成缺列。
- **降级动作**（`fetchRemotePage()`）：确认缺列后记录 `recordColumnMissing` 和诊断，再改用旧列清单（`PULL_COLUMNS_LEGACY`，去掉 `record_updated_at`）**重试一次**；已有账本应走第十四节 prepare，而不是删表或把新库脚本当升级步骤：

  ```
  id,record_id,kind,data,updated_at,deleted
  ```

- **已经降级还报缺列**：说明不是这一列的问题，按真实错误原样抛出，不吞错。
- **推送侧共用同一标志**：`buildPushPayload()` / `postWithSchemaFallback()` 见到 `recordColumnMissing` 后，后续批次直接从 payload 里省掉该列，不再每次都先撞一次 400；缺 `schema_version` 时同理（`schemaColumnMissing`）。
- 两侧都通过 `warnDegraded()` 写同一个 `yh-sync-warn` 键，只保留最后一次文案。
- **`yh-sync-warn` 现在可能是多行**：拉取到的远端行若没通过 `parseRemoteRecord()` 校验（必填字段缺失、类型不对、枚举越界、`qtyBase<=0` 等），会被**跳过不落库**，并往这个键追加一行「拉取到非法数据已跳过：`kind`:`recordId`」；相同文案去重，按写入顺序**最多保留 20 条**。所以看到多行只说明「远端有脏数据被跳过」，不等于同步失败；降级告警仍是单条、只保留最后一次。排查完可手动 `localStorage.removeItem('yh-sync-warn')`。

降级只是「还能用」，不是「正常」：

- 缺 `record_updated_at` 时，冲突判定退回记录自身的业务时间（`data.updatedAt`），与旧客户端的判定口径一致；
- 缺 `schema_version` 时，远端按列默认值 `1` 存，远端也就分不清记录格式版本。

有降级说明远端结构仍需处理；按第十四节迁移并验证实际能力，再观察诊断。缺列回退只覆盖对应旧列兼容，不能替代复合主键、清云 RPC、current epoch 或条件重连上传能力。

## 十四、分阶段升级（2026-11 稳定性修复候选）

### 迁移正本与执行顺序

| 对象 | 正本 | 边界 |
|---|---|---|
| 新建空库 | [schema.sql](../supabase/schema.sql) | 直接建立 `(ledger,id)` 主键及协议对象；设置页显示/复制同一文件 |
| 已有旧账本，准备阶段 | [prepare](../supabase/migrations/2026-11-13-stability-prepare.sql) | 显式补列、建立 `(ledger,id)` 唯一索引与 RPC/RLS；保留原 `id` 主键 |
| 两台设备确认升级后 | [finalize](../supabase/migrations/2026-11-13-stability-finalize.sql) | 检查约束并切实际主键为 `(ledger,id)`，能力从实际目录状态推导，提交后方可启用账本切换/清云 |

1. 两台各导出可读取的 JSON，维护者保存云端备份与当前约束/策略清单。所有迁移先在独立测试库运行；本轮交付不执行生产迁移。
2. 旧库执行 prepare，显式补 `record_updated_at` / `schema_version` / `clear_epoch`；检查历史行保留、旧 `id` 主键仍在、复合唯一索引与补列正确。`CREATE TABLE IF NOT EXISTS` 不会修正旧表，不能省成重跑新库脚本。
3. 经最终门禁后再由获授权维护者发布兼容前端。两台在“设置 → 应用更新”确认更新，逐台记录构建标识、同步与待推送结果；此时旧主键仍保留，不演练清云或换账本。
4. **两台实际设备都确认升级**，且独立测试库 SQL/RLS、实际 PostgREST HTTP、并发验收满足要求后，维护者才人工执行 finalize；不能让 Agent 根据浏览器 mock 自动勾选。
5. 核对实际主键与 `yh_sync_capabilities` 返回；再只在独立测试账本验证相同业务 id 的双账本 upsert、clear receipt、未知结果同号重试、旧 epoch 拒绝及条件重连写。重新接入上传还要求 `yh_reconcile_push` 的额外能力/receipt 合同，不能用单一 protocolVersion 代替。

### 约束阻塞与能力核对

finalize 检查真正的 PK、外部 FK、无 ledger 作用域的 UNIQUE（含表达式/部分索引/INCLUDE）与 EXCLUDE；遇到未知约束会拒绝并回滚，先审核，不用 `CASCADE`、删冲突行或清账本解决。PostgREST schema cache 需按迁移中的 reload 通知刷新，再用实际 HTTP 验证复合冲突目标和请求头。

未执行生产迁移、未发布候选、未真机验收都必须单列“未完成”；SQL/WASM 成功不能证明实际 HTTP 或多连接并发已验证。

### 幂等不替代迁移

prepare / finalize 可重复检查正确状态；幂等不表示能跳过约束审核。新库正本用于新库，旧库依次使用 prepare / finalize，不删表重建，不以重跑旧脚本代替协议迁移。

### 只读结构验证

```sql
select c.conname, c.contype, pg_get_constraintdef(c.oid)
from pg_constraint c where c.conrelid = 'public.yh_records'::regclass;

select indexname, indexdef from pg_indexes
where schemaname = 'public' and tablename = 'yh_records';

select column_name, data_type, column_default from information_schema.columns
where table_schema = 'public' and table_name = 'yh_records'
  and column_name in ('record_updated_at', 'schema_version', 'clear_epoch');
```

prepare 后保留旧 `PRIMARY KEY (id)` 并有复合唯一索引；finalize/新库后应为 `PRIMARY KEY (ledger,id)`。还需核对第十节策略、函数权限和能力响应；独立验收命令见[运维手册](08-运维手册.md#12-本轮候选的本地门禁与交付边界)。

### 回滚与现场保留

- finalize 前可停止后续迁移并保留备份和兼容前端；不要恢复开放 RLS 或重新授予 anon DELETE。
- **复合主键落地后不能回退到只用 `on_conflict=id` 的旧前端**；保留协议兼容的上一构建，优先前向修复。多账本已有相同 id 后不能强行恢复全表 id 唯一，禁止删业务行来凑回滚条件。

- 清云/重连失败先停同步、导出现场，保留 operationId、receipt、epoch 和错误；未知结果只重试原操作，不另起清空，不删协议内部行来“重置”。
