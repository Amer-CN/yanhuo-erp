# 云同步设置（Supabase）

> 目标：**云端有一份主账，离线照常开单，联网自动推拉**。
> 本机始终是“可离线工作的副本”；手动导出/导入降级为备份手段。

## 零配置（默认，开箱即用）

应用已经内置了项目 URL、publishable key 和同步码。**两台手机打开同一个网址就自动是同一本账，不需要填任何东西**。

- 设置页会显示「配置：内置，打开即用」
- 想换自己的同步码：设置与同步 → 云同步 → 修改配置（两台手机都换）
- 注意：内置同步码会随公开仓库的前端代码发布，理论上懂技术的人翻代码能看到；如果在意隐私，请换成自己的同步码

下面的手工配置步骤只在“换项目 / 换同步码”时需要。

## 一、为什么需要 Supabase

GitHub Pages 只能放静态文件，存不了账。Supabase 提供免费的 Postgres 数据库 + REST 接口，正好当同步后端。两台手机共用同一个 Supabase 项目和一个同步码。

## 二、配置步骤（约 3 分钟）

1. 打开 <https://supabase.com>，用 GitHub 登录，`New project`：
   - 名称随意，数据库密码记一下（后面一般不用）
   - Region 选 **Singapore**（离国内近）
   - 等 1 分钟项目初始化
2. 左侧 `SQL Editor` → 新建查询 → 把 [`supabase/schema.sql`](../supabase/schema.sql) 整段粘贴执行。
3. 左侧 `Project Settings → API`：
   - 复制 **Project URL**（形如 `https://xxxx.supabase.co`）
   - 复制 **anon public key**
4. 手机打开烟花账 → `更多 → 设置与同步` → **云同步**：
   - 填 Project URL、anon key
   - 点「生成」得到一个同步码
   - 「保存并启用」
5. 第二台手机填**同样的 URL、anon key、同步码**，保存启用。

两台都显示「已连接」后，一台开单，另一台几秒到十几秒内会自动看到。

## 三、自动同步的时机

- 打开 App / 切回前台
- 网络从断开变连通
- 每成交一单（本地写完后约 0.7 秒推送）
- 每 10 秒拉取一次对方的新记录

本地写入永远先成功，网络只影响“什么时候同步出去”，不影响开单。

## 四、同步什么、不同步什么

| 数据 | 同步 | 规则 |
|---|---|---|
| 商品 | 是 | 按 `updatedAt` 后写胜 |
| 进货批次 | 是 | UUID 并集，不覆盖 |
| 销售单/明细 | 是 | UUID 并集，只增不改；作废是订单上的标记 |
| 库存调整 | 是 | UUID 并集 |
| 设置（操作人、临期天数等） | 是 | 后写胜 |
| 设备名 / 设备 ID | 否 | 每台设备自己的身份 |

删除用“墓碑”记录（`deleted=true`）同步，另一端会删掉对应本地记录。

## 五、安全说明

- 自定义配置的 `anon key` 和同步码只存在手机本地（localStorage）；**内置配置**的 URL / publishable key / 同步码会随前端包公开，**不是秘密**（见第八节）。
- 数据库用 RLS 策略校验请求头 `x-ledger-key`：只有带着正确同步码的请求能读写对应账本。
- 不要退回 `using (true)` 策略：那等于允许任何持有 anon key 的客户端读写全部账本（`supabase/schema.sql` 末尾有警告）。
- 想换同步码：改两台手机的同步码即可；旧数据留在旧账本下，不会自动迁移。轮换步骤见第八节。

## 六、常见问题

| 现象 | 排查 |
|---|---|
| 保存后显示「同步出错」 | 先点「测试连接」；确认 SQL 执行过、URL/key 没抄错 |
| 401 / 403 | 多半是 RLS 策略没建好，或 key 不是 anon public key |
| 一直「待推送 N 条」 | 检查网络；Supabase 免费项目长时间不用会暂停，去控制台恢复 |
| 第二台看不到新单 | 确认两台同步码完全一致（大小写/空格）；点「立即同步」试 |
| 一台清空后另一台还是老数据 | 按第十一节的「一台清空后另一台没清空」四步自查：两台是否都升级到本版 → 标记行是否被 RLS 拦住 → `yh-sync-warn` 是否有内容 → 是否离线未同步 |
| 数据想清空重来 | 设置与同步 → 清空全部数据，会问是否同时清云端 |

## 七、和手动备份的关系

手动「导出备份 / 导入合并」保留，用于：

- 云端出问题时的兜底
- 换手机/重装时恢复
- 存一份到微信收藏

云同步正常时不需要再手动合并。

## 八、凭据公开性与轮换

### 公开性（重要）

- 应用内置的 `url`、`anonKey`（publishable key）和 `ledgerKey`（同步码）**都会被打进公开的前端产物**：仓库是公开的，GitHub Pages 上的 JS 也能直接下载。它们**不是秘密**，不能当密码用。
- `anonKey` 不是数据库管理员密钥，但配合 `ledgerKey` 已足够读写**本账本**的数据。

### 当前 RLS 的实际保证边界

- 能阻止：没有本账本 `ledgerKey` 的客户端访问本账本（跨账本隔离）。
- 不能阻止：任何拿到本账本 `ledgerKey` 的人读写本账本。账本隔离是「一本账一把钥匙」，不是「一把钥匙只给你」。
- 因此：不要把 `anonKey` 或同步码发到公开 issue、群聊、截图里；**不要**把 RLS 改成 `using (true)`（等于取消账本隔离，见 `supabase/schema.sql` 末尾警告）。

### 轮换步骤（对应执行计划 docs/06 §7-A；必须两台设备同时在场，先导出备份）

1. 在其中一台手机上：`更多 → 设置与同步 → 云同步`，先「导出备份」并确认文件能打开。
2. 确认另一台手机也在场、电量充足、能联网。
3. 两台手机分别打开「修改配置」，把同步码改成**同一串新的**随机值（建议 32 位以上），保存并启用。
4. 旧账本数据仍留在旧同步码下，不会自动迁移；确需迁移时，用备份导入新账本后再核对金额。
5. 轮换完成后，两台手机各开一单，确认能互相看到。

> 红线：轮换会让另一台手机立即失联，必须两台一起改；轮换前先备份。

## 九、升级到复合游标（2026-11，协议变更）

拉取水位从「单列 `updated_at`」改为「`(updated_at, id)` 复合游标」。

**为什么**：推送时同一批记录会取到相同的毫秒时间戳。旧实现用 `updated_at=gt.{since}` 翻页，一旦一页的首尾时间戳相同、同毫秒的记录又超过 500 条，剩下的会被**永久跳过**，且不会自愈。

### 升级步骤

1. **先在 Supabase 控制台建索引**（不建也能用，但同时间戳数据多时翻页会变慢）：

   ```sql
   create index if not exists yh_records_ledger_updated_id
     on public.yh_records (ledger, updated_at, id);
   ```

   完整脚本见 [`supabase/schema.sql`](../supabase/schema.sql)，`if not exists` 可重复执行。

2. 再更新两台手机的前端（刷新页面 / 等 PWA 自动更新）。

> ⚠️ **两端必须一起升级**：仍跑旧版本的客户端继续用 `gt` 单列游标，在「同毫秒超过一页」的场景下仍可能丢记录。新老客户端共用同一张表、同一套列，数据格式没有变化，因此**可以**暂时混跑（不会写坏数据），但不要长期让旧客户端留在弱网/大批量补发场景里。

### 兼容说明

- 旧的 `localStorage['yh-sync-last-pull']`（时间水位）继续保留；新增 `localStorage['yh-sync-last-pull-id']` 保存游标 id。
- 老版本升级上来时没有 id 水位，首次拉取按 `updated_at=gte.{ts}` 重放该毫秒的记录：**不会因为升级丢一轮数据**，重复应用是幂等的。
- 清空同步配置（`clearSyncConfig`）会同时清掉两个水位键，以及第十二节提到的清空标记 `yh-sync-cleared-at`。
- 本版 `schema.sql` 会先建三列索引、再 `drop index if exists yh_records_ledger_updated` 收敛旧的两列索引；升级顺序见第十四节。

## 十、收紧云端权限（2026-11，撤销 anon 删除）

v2 策略把「一把钥匙开到底」改成「**只能读、增、改，不能物理删除**」。

### 改了什么

| 项 | v1 | v2 |
|---|---|---|
| anon 的 `DELETE` | 允许 | **撤销** |
| RLS 策略 | 一条 `for all` | `select` / `insert` / `update` 三条 |
| 客户端「清空云端」 | `DELETE` 整表 | `PATCH` 把 `deleted` 置 true（软删除），再 upsert 一条 `__ledger_cleared__:<同步码>` 标记行（见第十一节） |

为什么：账本同步码是打在前端包里的公开值（见第八节）。撤销 `DELETE` 之后，即使别人拿到它，也只能读到你的账本，**不能一键抹掉**。这是在不改变「打开即用」体验的前提下，能拿到的最大一块安全收益。

### 上线顺序（顺序反了会 403）

1. **先发新版前端**（本仓库的 `clearCloud` 已改为 `PATCH`）。
2. 两台手机都刷新到新版，确认能正常同步。
3. 再在 Supabase → SQL Editor 执行 [`supabase/schema.sql`](../supabase/schema.sql) 整段（`if not exists` / `drop policy if exists` 都可重复执行）。

> 新版前端 + 旧策略 = 正常（旧 `for all` 本来就允许 update）；
> 旧版前端 + 新策略 = 「清空云端」返回 403。所以**前端必须先发**。

> 上面这个顺序只针对 **v1 → v2 这一步**（旧前端会用 `DELETE` 清空）。账本已经跑过 v2 策略之后，本版（清空标记行 / 复合游标）的顺序**反过来**：先重跑 `schema.sql`，再更新前端，见第十四节。

### 执行前备份

在两台手机上各导出一份 JSON（设置 → 本地备份 / 手动导出），或用 SQL Editor 存一份快照：

```sql
select * from public.yh_records order by updated_at;
```

### 验证

```sql
-- 1. 策略已拆开：应看到 yh ledger read / write / update 三条，没有 yh ledger access
select polname, polcmd from pg_policy where polrelid = 'public.yh_records'::regclass;

-- 2. anon 没有 DELETE：结果应为空
select grantee, privilege_type
from information_schema.role_table_grants
where table_name = 'yh_records' and grantee = 'anon' and privilege_type = 'DELETE';
```

再从命令行确认物理删除被拒（预期 401 / 403）：

```powershell
curl.exe -i -X DELETE "https://<项目>.supabase.co/rest/v1/yh_records?ledger=eq.<同步码>" -H "apikey: <publishable key>" -H "x-ledger-key: <同步码>"
```

顺带跑一次仓库自带的探测脚本（它已改成用软删除收尾）：

```powershell
node scripts/probe-supabase.mjs
```

### 副作用与回滚

- **软删除不释放存储**：行会一直保留（`deleted=true`）。自用数据量小可忽略；要彻底清，用 `service_role` 在控制台执行物理删除（它 bypass RLS）。
- 清空后重新开张：新记录用新 UUID，旧行只是被标记，不影响任何统计。
- 回滚 SQL 写在 [`supabase/schema.sql`](../supabase/schema.sql) 末尾的注释里（`grant delete` + 恢复 `for all` 策略），执行后旧客户端即可继续用 `DELETE` 清空——但「任意持码者可清空账本」的风险也会一起回来。

## 十一、清空账本的协议：软删除 + 标记行（2026-11，协议变更）

以前「清空云端」只发一条 `PATCH` 把本账本的行标成 `deleted: true`。软删除本质上是一条普通变更，只能靠 `updated_at` 水位传给另一台手机，于是有两种永远拉不到的情况：

- 另一台手机**时钟偏快**，它的水位比这次软删除的 `updated_at` 还大，墓碑落在水位以下，永远拉不到；
- 墓碑的 `updated_at` 与对方水位**落在同一毫秒**，而增量拉取只取「严格大于水位」的行。

两种情况都**不会自愈**。所以清空改成两步，第二步专门负责「通知另一台手机」。

### 第一步：批量软删除（前端永不发 `DELETE`）

```http
PATCH /rest/v1/yh_records?ledger=eq.<ledger-key>
Prefer: return=minimal

{ "deleted": true, "updated_at": <clearedAt> }
```

- 一次请求把**本账本**所有行打成墓碑，同时刷新 `updated_at`。
- 服务端 v2 起撤销了 `anon` 的 `DELETE`（第十节），客户端**永远不发 `DELETE`**。

### 第二步：upsert 一条固定 id 的标记行

```http
POST /rest/v1/yh_records?on_conflict=id
Prefer: resolution=merge-duplicates,return=minimal

[ { "id": "__ledger_cleared__:<ledger-key>",
    "record_id": "__ledger_cleared__:<ledger-key>",
    "ledger": "<ledger-key>",
    "kind": "ledger",
    "data": { "clearedAt": <clearedAt> },
    "updated_at": <clearedAt>,
    "deleted": false } ]
```

- id 固定为 `__ledger_cleared__:` + 同步码（代码常量 `CLEAR_MARKER_PREFIX`，`kind` 为 `ledger`）。带同步码是因为 id 是远端主键，多个账本共用一张表时不能互相覆盖。
- `record_id` 与 id 同值、`ledger` 必须等于同步码（`record_id` / `ledger` 都是非空列，RLS 也用 `ledger` 校验）。
- `on_conflict=id` + `merge-duplicates` 就是 upsert：反复清空只更新这一条，不会越积越多。
- 标记行不写 `record_updated_at` / `schema_version`，靠列的默认值也能写进没升级的远端。
- `clearCloud()` 里 `clearedAt = Date.now()`，PATCH 与标记行用同一个值。

### 另一台手机为什么能收到

每次拉取**开始前**先探一次标记行（`readClearMark()`）：

```http
GET /rest/v1/yh_records?id=eq.<__ledger_cleared__:ledger-key>&select=id,updated_at,data&limit=1
```

- 标记的值（`data.clearedAt`，缺失时退回 `updated_at`）与本机 `localStorage['yh-sync-cleared-at']` **不同** → 把游标 `yh-sync-last-pull` / `yh-sync-last-pull-id` 归 0，做**一次全量重放**（`resolvePullStart()`）。
- 全量重放是幂等的：墓碑会把本地对应记录删掉，重复应用不会写坏数据，代价只是多拉一轮。
- 因此清空**不再依赖两台手机时钟一致**，也不受「墓碑与本地游标同毫秒」影响。
- 本机水位本来是 0 时不再多打这次探测（反正要全量拉）。
- 先落盘标记值、再重置游标：即使这一轮中途失败，也不会反复重置、卡在同一份全量重放上。
- 读不到标记行（旧库 / 无权限 / 网络问题）时返回 0，按普通增量继续——标记只是兜底，绝不阻断同步，更不能阻断开单。

### 标记行是协议内部行

| 行为 | 说明 |
|---|---|
| 写入业务表 | 不会。`pull()` 用 `isClearMarkerRow()` 按 id 前缀整行过滤 |
| 计入拉取条数 | 不会。`pulled` 只统计过滤后的业务行 |
| 进 `sync-unknown-kinds` 诊断 | 不会。新版先过滤、再统计未知 kind |
| 旧版客户端 | 只会把它当成未知 kind 记进诊断（最多保留 20 条 id），不污染账本、不影响功能 |

### 一台清空后另一台没清空（按顺序自查）

1. **两台都升级到本版了吗**：只有一台是新版时，旧版没有「探标记行 + 重放」的逻辑，可能收不到这次清空。
2. **标记行的 `GET` 是否被 RLS 拦住**：请求必须同时带 `apikey` 与 `x-ledger-key`（头部写法见第十节的 `curl.exe` 示例）。同步码不一致（大小写、空格）就读不到标记，也就不会重放。
3. **`localStorage['yh-sync-warn']` 是否有内容**：控制台执行 `localStorage.getItem('yh-sync-warn')`。有文案说明远端缺列降级了，见第十三节。
4. **是否离线未同步**：还在离线 / 本地「待推送 N 条」没发出去，联网后点「立即同步」再看一次。

以上都对仍不行：先在两台各导出一份备份，再用 SQL 确认墓碑确实写进远端：

```sql
select count(*) filter (where deleted) as tombstones, count(*) as total
from public.yh_records
where ledger = '<ledger-key>';
```

## 十二、本地存储键清单（localStorage）

云同步的状态全在手机本地的 `localStorage` 里，键名统一用 kebab-case。排查问题时对照此表看值即可（控制台：`localStorage.getItem('yh-sync-last-pull')`）。表里只列 `src/db/sync.ts` 的 `LS` 表里真实存在的键。

| 键 | 用途 | `clearSyncConfig()` 是否清除 |
|---|---|---|
| `yh-sync-url` | Supabase 项目 URL（自定义配置才有；内置配置不写） | 是 |
| `yh-sync-anon` | `anon` / publishable key | 是 |
| `yh-sync-ledger` | 同步码，即 RLS 校验的 `x-ledger-key` | 是 |
| `yh-sync-last-pull` | 拉取水位：`updated_at` 部分（毫秒） | 是 |
| `yh-sync-last-pull-id` | 拉取水位：同毫秒时的 id 部分（复合游标第二列） | 是 |
| `yh-sync-cleared-at` | **新增**：已处理过的「清空标记」值。远端标记换成新值 → 游标归 0 全量重放一次 | 是 |
| `yh-sync-last-sync` | 上次同步成功的时间戳（设置页展示「已连接」） | 是 |
| `yh-sync-error` | 最近一次同步的错误文案，同步成功后清除 | 是 |
| `yh-sync-warn` | **新增**：诊断文案，可能是**多行**（换行分隔）。降级告警为单条；非法远端行为「拉取到非法数据已跳过：`kind`:`recordId`」，最多 20 条。只写不改；目前**不在界面上展示**，只能在控制台读 | 否 |
| `yh-sync-disabled` | 值为 `1` 表示停用云同步（E2E / 测试脚本用它避免写真实账本） | 置为 `1` |

补充说明：

- `yh-sync-cleared-at` 必须跟着 `clearSyncConfig()` 一起清掉：换了同步码就是换了账本，带着旧账本的标记值会被误判成「这次清空已经处理过」，从而跳过本该做的全量重放。
- `yh-sync-warn` 不清除是刻意的（它记录的是远端结构问题，不属于某个同步码）；但如果远端已重跑新版 `schema.sql`、告警文案还挂着，可以手动 `localStorage.removeItem('yh-sync-warn')` 清掉再看。
- 未知记录类型的诊断 `sync-unknown-kinds` **不是** localStorage 键，而是本地设置表里的一条记录（`deviceId` / `deviceName` 同级），不上云。

## 十三、旧远端缺列的降级与告警

远端没重跑新版 [`supabase/schema.sql`](../supabase/schema.sql) 时，`yh_records` 表里没有 `record_updated_at` 列，而新版拉取用的是显式列清单（`PULL_COLUMNS`）：

```
id,record_id,kind,data,updated_at,record_updated_at,deleted
```

PostgREST 遇到不存在的列会直接 400，整条同步链会被一次 400 打挂。所以拉取侧做了和推送侧对称的降级：

- **只在确认缺列时降级**：`pullRecordColumnMissing()` 要求错误文本里同时出现 `record_updated_at` 与 `PGRST204` / `42703` / `does not exist` / `schema cache` 之一，避免把网络抖动当成缺列。
- **降级动作**（`fetchRemotePage()`）：置 `recordColumnMissing = true`，用 `warnDegraded()` 写 `yh-sync-warn`：「远端缺少 record_updated_at 列，拉取已降级；升级请先执行新版 supabase/schema.sql」，然后改用旧列清单（`PULL_COLUMNS_LEGACY`，去掉了 `record_updated_at`）**重试一次**：

  ```
  id,record_id,kind,data,updated_at,deleted
  ```

- **已经降级还报缺列**：说明不是这一列的问题，按真实错误原样抛出，不吞错。
- **推送侧共用同一标志**：`buildPushPayload()` / `postWithSchemaFallback()` 见到 `recordColumnMissing` 后，后续批次直接从 payload 里省掉该列，不再每次都先撞一次 400；缺 `schema_version` 时同理（`schemaColumnMissing`）。
- 两侧都通过 `warnDegraded()` 写同一个 `yh-sync-warn` 键，只保留最后一次文案。
- **`yh-sync-warn` 现在可能是多行**：拉取到的远端行若没通过 `parseRemoteRecord()` 校验（必填字段缺失、类型不对、枚举越界、`qtyBase<=0` 等），会被**跳过不落库**，并往这个键追加一行「拉取到非法数据已跳过：`kind`:`recordId`」；相同文案去重，按写入顺序**最多保留 20 条**。所以看到多行只说明「远端有脏数据被跳过」，不等于同步失败；降级告警仍是单条、只保留最后一次。排查完可手动 `localStorage.removeItem('yh-sync-warn')`。

降级只是「还能用」，不是「正常」：

- 缺 `record_updated_at` 时，冲突判定退回记录自身的业务时间（`data.updatedAt`），与旧客户端的判定口径一致；
- 缺 `schema_version` 时，远端按列默认值 `1` 存，远端也就分不清记录格式版本。

只要还在降级，`yh-sync-warn` 就会一直有内容。按第十四节重跑一次脚本即可消除。

## 十四、升级到本版本（2026-11）

### 红线：先在 Supabase 重跑 `schema.sql`，再更新前端

1. 打开 Supabase 控制台 → `SQL Editor` → 新建查询。
2. 把 [`supabase/schema.sql`](../supabase/schema.sql) **整段**粘贴执行。
3. 确认无报错后，再更新两台手机的前端（刷新页面 / 等 PWA 自动更新）。
4. 两台手机各开一单，确认能互相看到。需要顺带验证清空链路时，**先导出备份**，或换一个临时同步码当测试账本再试。

顺序反了会怎样（三条理由，都是「能跑但不对劲」，不会写坏数据）：

| 理由 | 少了什么 | 现象 |
|---|---|---|
| ① 游标翻页依赖三列索引 `yh_records_ledger_updated_id` | 本版脚本会 `drop index if exists yh_records_ledger_updated` 收敛旧的两列索引 | 新前端用 `(updated_at, id)` 复合游标翻页，没有三列索引时只能扫更多行，大账本/补发时明显变慢 |
| ② 缺 `record_updated_at` 列会触发降级 | 拉取 400 → 改用旧列清单重试（第十三节） | 能跑，但 `yh-sync-warn` 持续有内容，冲突判定退回 `data.updatedAt` |
| ③ 清空标记行要求 `yh_records` 可 upsert | `grant select, insert, update` + `select` / `insert` / `update` 三条 RLS 策略（禁 `delete`） | 标记行写不进去 → 另一台手机收不到清空；权限策略还是 v1 的 `for all` 时则「任意持码者可清空」的风险仍在 |

> 例外：如果这台账本还停在 **v1 策略**（从没执行过第十节的脚本），那一步必须**前端先发**，否则旧前端用 `DELETE` 清空会 403。v1 已升到 v2 之后，本版才是「脚本先行」。

### 脚本是幂等的

`supabase/schema.sql` 可以**重复整段执行**，不需要先删表：

- `create table if not exists` / `create index if not exists` / `drop index if exists`；
- 策略先 `drop policy if exists`（四个旧名字都列了）再 `create policy`，重复执行不会撞名；
- `grant select, insert, update` / `revoke delete` 对同一对象重复执行结果不变。

### 验证

```sql
-- 1. 三列索引在、旧的两列索引已删
select indexname from pg_indexes where tablename = 'yh_records' order by indexname;

-- 2. record_updated_at 列在
select column_name, data_type, column_default
from information_schema.columns
where table_name = 'yh_records' and column_name = 'record_updated_at';

-- 3. 策略是拆开的三条（不应再有 yh ledger access）
select polname, polcmd from pg_policy where polrelid = 'public.yh_records'::regclass;
```

预期：索引里有 `yh_records_ledger_updated_id` / `yh_records_ledger_record_updated`，没有 `yh_records_ledger_updated`；策略是 `yh ledger read` / `write` / `update`。

### 回滚

- **索引回滚**（前端退回旧版本时恢复两列索引，可重复执行）：

  ```sql
  create index if not exists yh_records_ledger_updated
    on public.yh_records (ledger, updated_at);
  ```

- **策略回滚**：SQL 写在本仓库 `supabase/schema.sql` 末尾注释里（`grant delete` + 恢复 `for all`），执行后旧客户端可继续用 `DELETE` 清空——但「任意持码者可清空账本」的风险一起回来。
- **前端回滚后标记行怎么办**：不用管。旧版不会写标记行，残留的 `__ledger_cleared__:*` 行对旧版只是一个未知 `kind`（记进 `sync-unknown-kinds` 诊断，最多 20 条 id），不影响开单、报表与同步。真要删，用 `service_role` 在控制台删这几行即可（`anon` 没有 `DELETE`）。
