# 云同步设置（Supabase）

> 目标：**云端有一份主账，离线照常开单，联网自动推拉**。
> 本机始终是“可离线工作的副本”；手动导出/导入降级为备份手段。

## 零配置（默认，开箱即用）

应用已经内置了项目 URL、publishable key 和同步码。**两台手机打开同一个网址就自动是同一本账，不需要填任何东西**。

- 设置页会显示「配置：内置，打开即用」
- 想换自己的同步码：设置与同步 → 云同步 → 修改配置（两台手机都换）
- 注意：内置同步码会随公开仓库的前端代码发布，理论上懂技术的人翻代码能看到；如果在意隐私，请换成自己的同步码

下面的手工配置步骤只在“换项目 / 换同步码”时需要。

## 一、为什么需要 Supabase

GitHub Pages 只能放静态文件，存不了账。Supabase 提供免费的 Postgres 数据库 + REST 接口，正好当同步后端。两台手机共用同一个 Supabase 项目和一个同步码。

## 二、配置步骤（约 3 分钟）

1. 打开 <https://supabase.com>，用 GitHub 登录，`New project`：
   - 名称随意，数据库密码记一下（后面一般不用）
   - Region 选 **Singapore**（离国内近）
   - 等 1 分钟项目初始化
2. 左侧 `SQL Editor` → 新建查询 → 把 [`supabase/schema.sql`](../supabase/schema.sql) 整段粘贴执行。
3. 左侧 `Project Settings → API`：
   - 复制 **Project URL**（形如 `https://xxxx.supabase.co`）
   - 复制 **anon public key**
4. 手机打开烟花账 → `更多 → 设置与同步` → **云同步**：
   - 填 Project URL、anon key
   - 点「生成」得到一个同步码
   - 「保存并启用」
5. 第二台手机填**同样的 URL、anon key、同步码**，保存启用。

两台都显示「已连接」后，一台开单，另一台几秒到十几秒内会自动看到。

## 三、自动同步的时机

- 打开 App / 切回前台
- 网络从断开变连通
- 每成交一单（本地写完后约 0.7 秒推送）
- 每 10 秒拉取一次对方的新记录

本地写入永远先成功，网络只影响“什么时候同步出去”，不影响开单。

## 四、同步什么、不同步什么

| 数据 | 同步 | 规则 |
|---|---|---|
| 商品 | 是 | 按 `updatedAt` 后写胜 |
| 进货批次 | 是 | UUID 并集，不覆盖 |
| 销售单/明细 | 是 | UUID 并集，只增不改；作废是订单上的标记 |
| 库存调整 | 是 | UUID 并集 |
| 设置（操作人、临期天数等） | 是 | 后写胜 |
| 设备名 / 设备 ID | 否 | 每台设备自己的身份 |

删除用“墓碑”记录（`deleted=true`）同步，另一端会删掉对应本地记录。

## 五、安全说明

- 自定义配置的 `anon key` 和同步码只存在手机本地（localStorage）；**内置配置**的 URL / publishable key / 同步码会随前端包公开，**不是秘密**（见第八节）。
- 数据库用 RLS 策略校验请求头 `x-ledger-key`：只有带着正确同步码的请求能读写对应账本。
- 不要退回 `using (true)` 策略：那等于允许任何持有 anon key 的客户端读写全部账本（`supabase/schema.sql` 末尾有警告）。
- 想换同步码：改两台手机的同步码即可；旧数据留在旧账本下，不会自动迁移。轮换步骤见第八节。

## 六、常见问题

| 现象 | 排查 |
|---|---|
| 保存后显示「同步出错」 | 先点「测试连接」；确认 SQL 执行过、URL/key 没抄错 |
| 401 / 403 | 多半是 RLS 策略没建好，或 key 不是 anon public key |
| 一直「待推送 N 条」 | 检查网络；Supabase 免费项目长时间不用会暂停，去控制台恢复 |
| 第二台看不到新单 | 确认两台同步码完全一致（大小写/空格）；点「立即同步」试 |
| 数据想清空重来 | 设置与同步 → 清空全部数据，会问是否同时清云端 |

## 七、和手动备份的关系

手动「导出备份 / 导入合并」保留，用于：

- 云端出问题时的兜底
- 换手机/重装时恢复
- 存一份到微信收藏

云同步正常时不需要再手动合并。

## 八、凭据公开性与轮换

### 公开性（重要）

- 应用内置的 `url`、`anonKey`（publishable key）和 `ledgerKey`（同步码）**都会被打进公开的前端产物**：仓库是公开的，GitHub Pages 上的 JS 也能直接下载。它们**不是秘密**，不能当密码用。
- `anonKey` 不是数据库管理员密钥，但配合 `ledgerKey` 已足够读写**本账本**的数据。

### 当前 RLS 的实际保证边界

- 能阻止：没有本账本 `ledgerKey` 的客户端访问本账本（跨账本隔离）。
- 不能阻止：任何拿到本账本 `ledgerKey` 的人读写本账本。账本隔离是「一本账一把钥匙」，不是「一把钥匙只给你」。
- 因此：不要把 `anonKey` 或同步码发到公开 issue、群聊、截图里；**不要**把 RLS 改成 `using (true)`（等于取消账本隔离，见 `supabase/schema.sql` 末尾警告）。

### 轮换步骤（对应执行计划 docs/06 §7-A；必须两台设备同时在场，先导出备份）

1. 在其中一台手机上：`更多 → 设置与同步 → 云同步`，先「导出备份」并确认文件能打开。
2. 确认另一台手机也在场、电量充足、能联网。
3. 两台手机分别打开「修改配置」，把同步码改成**同一串新的**随机值（建议 32 位以上），保存并启用。
4. 旧账本数据仍留在旧同步码下，不会自动迁移；确需迁移时，用备份导入新账本后再核对金额。
5. 轮换完成后，两台手机各开一单，确认能互相看到。

> 红线：轮换会让另一台手机立即失联，必须两台一起改；轮换前先备份。

## 九、升级到复合游标（2026-11，协议变更）

拉取水位从「单列 `updated_at`」改为「`(updated_at, id)` 复合游标」。

**为什么**：推送时同一批记录会取到相同的毫秒时间戳。旧实现用 `updated_at=gt.{since}` 翻页，一旦一页的首尾时间戳相同、同毫秒的记录又超过 500 条，剩下的会被**永久跳过**，且不会自愈。

### 升级步骤

1. **先在 Supabase 控制台建索引**（不建也能用，但同时间戳数据多时翻页会变慢）：

   ```sql
   create index if not exists yh_records_ledger_updated_id
     on public.yh_records (ledger, updated_at, id);
   ```

   完整脚本见 [`supabase/schema.sql`](../supabase/schema.sql)，`if not exists` 可重复执行。

2. 再更新两台手机的前端（刷新页面 / 等 PWA 自动更新）。

> ⚠️ **两端必须一起升级**：仍跑旧版本的客户端继续用 `gt` 单列游标，在「同毫秒超过一页」的场景下仍可能丢记录。新老客户端共用同一张表、同一套列，数据格式没有变化，因此**可以**暂时混跑（不会写坏数据），但不要长期让旧客户端留在弱网/大批量补发场景里。

### 兼容说明

- 旧的 `localStorage['yh-sync-last-pull']`（时间水位）继续保留；新增 `localStorage['yh-sync-last-pull-id']` 保存游标 id。
- 老版本升级上来时没有 id 水位，首次拉取按 `updated_at=gte.{ts}` 重放该毫秒的记录：**不会因为升级丢一轮数据**，重复应用是幂等的。
- 清空同步配置（`clearSyncConfig`）会同时清掉两个水位键。

## 十、收紧云端权限（2026-11，撤销 anon 删除）

v2 策略把「一把钥匙开到底」改成「**只能读、增、改，不能物理删除**」。

### 改了什么

| 项 | v1 | v2 |
|---|---|---|
| anon 的 `DELETE` | 允许 | **撤销** |
| RLS 策略 | 一条 `for all` | `select` / `insert` / `update` 三条 |
| 客户端「清空云端」 | `DELETE` 整表 | `PATCH` 把 `deleted` 置 true（软删除） |

为什么：账本同步码是打在前端包里的公开值（见第八节）。撤销 `DELETE` 之后，即使别人拿到它，也只能读到你的账本，**不能一键抹掉**。这是在不改变「打开即用」体验的前提下，能拿到的最大一块安全收益。

### 上线顺序（顺序反了会 403）

1. **先发新版前端**（本仓库的 `clearCloud` 已改为 `PATCH`）。
2. 两台手机都刷新到新版，确认能正常同步。
3. 再在 Supabase → SQL Editor 执行 [`supabase/schema.sql`](../supabase/schema.sql) 整段（`if not exists` / `drop policy if exists` 都可重复执行）。

> 新版前端 + 旧策略 = 正常（旧 `for all` 本来就允许 update）；
> 旧版前端 + 新策略 = 「清空云端」返回 403。所以**前端必须先发**。

### 执行前备份

在两台手机上各导出一份 JSON（设置 → 本地备份 / 手动导出），或用 SQL Editor 存一份快照：

```sql
select * from public.yh_records order by updated_at;
```

### 验证

```sql
-- 1. 策略已拆开：应看到 yh ledger read / write / update 三条，没有 yh ledger access
select polname, polcmd from pg_policy where polrelid = 'public.yh_records'::regclass;

-- 2. anon 没有 DELETE：结果应为空
select grantee, privilege_type
from information_schema.role_table_grants
where table_name = 'yh_records' and grantee = 'anon' and privilege_type = 'DELETE';
```

再从命令行确认物理删除被拒（预期 401 / 403）：

```powershell
curl.exe -i -X DELETE "https://<项目>.supabase.co/rest/v1/yh_records?ledger=eq.<同步码>" -H "apikey: <publishable key>" -H "x-ledger-key: <同步码>"
```

顺带跑一次仓库自带的探测脚本（它已改成用软删除收尾）：

```powershell
node scripts/probe-supabase.mjs
```

### 副作用与回滚

- **软删除不释放存储**：行会一直保留（`deleted=true`）。自用数据量小可忽略；要彻底清，用 `service_role` 在控制台执行物理删除（它 bypass RLS）。
- 清空后重新开张：新记录用新 UUID，旧行只是被标记，不影响任何统计。
- 回滚 SQL 写在 [`supabase/schema.sql`](../supabase/schema.sql) 末尾的注释里（`grant delete` + 恢复 `for all` 策略），执行后旧客户端即可继续用 `DELETE` 清空——但「任意持码者可清空账本」的风险也会一起回来。
