### 2.3 谁在第一视线

- 全页最大字号是 **34.5px** 的 hero 值：今天是毛利（y=153），本场是销售额/毛利（y=660）。
- 「今天销售额 ¥389.50」只出现在 **18px** 的卡标题里（y=87），不是 hero；用户第一眼看到的最大数字是「毛利 —」（成本待补）或「本场销售额 ¥16.00」。
- 对「收摊后看今天赚多少」：首屏 hero 是「—」时，用户必须先读标题里的 ¥389.50 和下方 12px 说明，才能知道今天卖了多少钱；「今天赚多少」的直接答案在视觉上是一个破折号。
- 对「中途确认这一场卖得怎么样」：本场销售额/毛利是 34.5px，位置也够（y=660），这一动线是成立的；但三行收款在 718–827，浮胶囊压在右侧，合计校验被 844 截断。

### 2.4 今天 vs 本场是否一眼分清

- 只在「本场 = 进行中」时成立：顶部 `统计范围：进行中这一场` + `22:00 → 进行中` 能区分今天合计与本场。
- 一旦没有进行中场次（收摊后最常见），`selected = openSession ?? closed[0]`（`ReportPage.tsx:718-721`）回退到最近已结账场次，但标签仍由 `mode` 决定（`:70-72`），于是出现「统计范围：进行中这一场」+ `09:05 → 21:30` 的自相矛盾（`08-no-open-has-closed.png`）。
- 两张卡金额完全相同时，唯一的区分是 12px 的「统计范围：…」和 18px 的「今天 · 已结账 N 场」；两个 34.5px 的大数字反而一样大，层级无法帮忙。

### 2.5 卡片顺序是否符合动线

- 「今天」卡固定第一、场次卡第二、单品表第三、临期第四：这个顺序对「收摊后先看今天」是对的，不应改（见第十节）。
- 但「今天」卡在 390×844 上高 456.5–480.5px，吃掉 58.5%–61.6% 的内容视口；本场卡的单数/让利/赠品（y≈873–899）和已排除行（y≈982–991）全部在首屏外。中途想确认「这一场卖了几单、让了多少」时要滚动一次（P2-8）。
- 操作条被放在单品卡底部，导致「复制本场汇总」要跨过 8 行表格；这与卡片顺序是两回事，见第三节。

### 3.2 操作位置结论

- **错的只有一组：`.report-actions`**。它挂在单品卡底部（`:537-564`），但两个按钮都是对「本场汇总」的操作，不是对表格的操作；在 8 行表格下实测距离 1223px。正确位置是本场卡内、hero 下方或说明文字之后（`:371-373` 一带），或做成紧贴本场卡的 44px 操作条。
- **对的**：今天排除行的「点开看」、卡头「补记」、表头排序、Sheet 行、删除单行内「撤销」都在作用对象旁。
- **可优化但不算错位**：浮胶囊是页面级控件，不需要紧邻某一个数字；它的问题在文案/遮挡，不在位置本身（保留底部拇指区）。

### 4.3 本轮新增的 P1 重复/缺失

- **P1-6 已结账状态不可辨**：`sessionRange`（`:40-47`）对已结账只写 `09:05 → 21:30`，进行中写 `→ 进行中`；`SessionScopeLabel`（`:70-75`）只有「进行中这一场」或「11-12 场」，场次卡没有「已结账」徽标。今天卡的「已结账 N 场」（`:157`）是日汇总，不是当前场次状态。用户只能靠 12px 的时间范围猜这一场结没结；实测 `08-no-open-has-closed.png` 里它甚至猜错。
- **P1-7 今天合计跨设备、场次列表只本机**：`closed` 用 `deviceSessions` 过滤（`:675-693`），Sheet 只列本机（`:918-953`）；`dayReport` 用全部 `sessions`（`:699-702`），`todayClosedIds` 也不过滤（`:705-711`）。双设备实测今天 2 场 ¥439.50，Sheet 只有 1 场 ¥389.50，另一台手机的 ¥50.00 无法下钻。
- **P1-8 「合计校验 ✓」恒真、复制文本不含警告**：`revenueFen` 与三收款都来自同一批 `order.totalFen`（`calc.ts:207-212`），`payTotal` 只是三项再相加（`:757`），正常数据永远 ✓；`copySummary`（`:781-805`）不包含 `payMismatch`。真实「现金少 50」不会触发，复制给对方的文本也不会带异常。
- **P1-9 两个「点开看」同文案不同范围**：今天行（`:199`）打开今天所有已结账场次的删除单；本场行（`:365`）只打开当前场次。单场今天时两个 Sheet 内容完全相同（两处都显示 2 笔 ¥15.00 / ¥68.00），用户无法从文案判断范围。
- **P2-7「补过 N 单」没有出口**：`:311-315` 是徽标，`:945` 只是 Sheet 行内文字，`:795` 只是复制文本的一行；用户想知道「补了哪几单」只能去「更多 → 销售记录」逐单找。不是重复入口，而是缺失入口。

### 6.2 四处真正的数字口径冲突

1. **汇总「—」 vs 单品「¥5.00~」（P0-3）**  
   `costMissing = summary.uncoveredQty > 0`（`:756`）只决定汇总 hero；`productMarginsBySession` 仍为每行算 `grossFen = revenue - cost`（`calc.ts:346`），成本缺失时 `costFen` 用 0/均价估算，行上只加 `~`（`:527`）。实测成本全缺场景：汇总 `毛利（成本待补） —`，表格 `手持烟花棒 | 1 支 | ¥5.00 | ¥0.00 | ¥5.00~`（`13-cost-missing-all.png` / `13b-cost-missing-table.png`）。`~` 没有图例，`:371-373` 的说明只解释 FIFO 和公式，不解释 `~`。
2. **今天合计跨设备 vs 场次列表只本机（P1-7）**  
   `closed` 先按 `deviceSessions = sessions.filter(s => s.deviceId === deviceId)`（`:675-693`），Sheet 只列这些（`:918-953`）；但 `dayReport(sessions, ...)` 传的是全部 `sessions`（`:699-702`），`todayClosedIds` 也不过滤设备（`:705-711`）。实测双设备：今天卡「已结账 2 场 · ¥439.50」，Sheet 只有本机 1 场「16 单 · ¥389.50」；另一台手机的 ¥50.00 那场无法下钻（`16-cross-device-top.png` / `17-cross-device-picker.png`）。
3. **「合计校验 ✓」是恒等式，不是对账（P1-8）**  
   `sessionReport` 的 `revenueFen` 与 `cashFen/wechatFen/alipayFen` 都来自同一个 `sel` 的 `o.totalFen`（`calc.ts:207-212`）；`payTotal` 只是把三个分项再相加（`:757`）。因此 `payMismatch` 在正常数据下永远为 `false`，绿色 ✓ 不能证明「现金箱里的钱对得上」。实测只有把 `totalFen` 写成字符串（模拟脏数据）才触发红色状态（`15-pay-mismatch-simulated.png` / `15b-pay-mismatch-status.png`）；正常录入不会出现。真实「现金少 50 元」需要用户自己数现金，页面没有输入实际现金的入口。
4. **复制文本不包含对账警告（P1-8）**  
   `copySummary`（`:781-805`）只拼 `销售额/三收款/毛利/让利/赠品/删除/补记`，没有 `payMismatch`，也没有「今天 or 本场」之外的校验提示。对账不符时页面红字警告，复制给对方的文本却是干净的；如果用户直接发微信对账，对方看不到异常。

> 另有 1 处不是「两个数字不同」而是标签错误：无进行中场次时，`selected` 回退到 `closed[0]`（`:718-721`），但 `SessionScopeLabel` 只看 `mode`（`:70-72`），把已结账场次写成「进行中这一场」。这会让用户把已结账金额当成进行中金额（P0-1）。

## 十、不做的事（哪些「看起来该改但其实是对的」）

1. **不要把「今天」卡移到场次卡下面，也不要让它参与场次切换。** `ReportPage.tsx:811-829` 的顺序是 H1 的修复：收摊后第一眼必须是今天已结账合计；场次切换只影响下面的明细卡。当前问题是内容重复（P0-1），不是顺序错。
2. **不要把进行中场次并进「今天」。** `calc.ts:354-362` 明确按 `closedAt` 累加；`ReportPage.tsx:134-141` 的「不计入今天」是对的。进行中金额单独一行，不要合并。
3. **不要把 `costMissing` 改回全局 `fifo.uncoveredQty`。** `ReportPage.tsx:748-756` 注释已说明：别的场次缺一批货会让今天整页毛利变「—」，那是 H2 的旧 bug。按场次判断是对的。
4. **不要因为排序标题问题删掉「缺成本置顶 + 成本待补徽标」。** `ReportPage.tsx:404-409, 489-501` 是 H3 的安全默认：缺成本行的毛利是估算，藏在正常行里会被当真。要改的是标题/排序语义（P2-3），不是撤掉徽标。
5. **不要给 `.glass-table-wrap` 重新加 `overflow-x: auto/hidden`。** `styles.css:1018-1039` 已解释：任何 overflow 都会让 `thead th` 的 sticky 失效；390 宽下表宽 328、不溢出，不需要横滚容器。将来真溢出，用列宽/`min-width` 解决。
6. **不要把浮胶囊挪回页面顶端。** `styles.css:1052-1058` 的实测：顶端 y≈87，收摊时单手够不到；底部 y=704–748 才是拇指区。要修的是遮挡和文案（P0-2 / D），不是位置。
7. **不要在窄屏把「让利 / 赠品」两列加回来。** `record.css:747-756` 取舍正确：让利总额在汇总卡、赠品写在商品名下，成本和毛利必须同屏。加回来会把毛利切掉。
8. **不要把「—」统一改成 0。** 毛利 `—` 是「未知/成本待补」，赠品 `—` 是「没有」；两者语义不同。要区分文案（P2-2），不是填 0。
9. **不要把删除单并回销售额。** `calc.ts:235-236, 270-276` 和 `ReportPage.tsx:110-131, 365-369` 的「已排除 N 笔」是 M1 的修复：删除单必须可见但不计入合计。正确。
10. **不要因为「历史视图也有今天卡」就把它藏掉。** 今天卡是日汇总锚点，历史视图下仍需要它；问题是无进行中时它和场次卡重复（P0-1），不是它不该出现。
11. **不要把临期预警按场次过滤。** `ReportPage.tsx:736-740` 用全部批次是库存视角，临期不是场次销售；按场次过滤会漏掉摊位上还没卖但快过期的货。
12. **不要因为「去记一笔」重复就删底栏「记账」tab。** 底栏是全局导航，任何页面都要有；该删的是 `ReportPage.tsx:556-562` 的页内按钮（B），不是 tab。
13. **不要把所有 11px 都改成 12px。** 底栏标签 11px 是 GlassKit 的固定规格；全页只有这 5 个 11px，改大反而挤坏底栏。审计只登记，不建议动。
14. **不要为 390 宽加横向滚动提示。** 表格 328 正好放下、无 `scrollWidth > clientWidth`；加提示会制造不存在的操作。只有将来表格真的变宽时才需要。
15. **不要以为「今天」和「本场」两张卡在单场时相同就是 bug。** 多场时它们确实不同；单场时相同是数据事实。真正的 bug 是无进行中时场次卡被错误标成「进行中」（P0-1），以及两张卡重复占首屏（P2-8）。
16. **不要把两个删除单 Sheet 当成重复功能删掉一个。** 「今天被删除的单」和「这一场被删除的单」在多场时范围不同，两个入口是必要的；单场今天时内容相同是正常的，只需在文案上写清范围（P1-9）。
