## 2. 唯一硬骨头：两台设备各自离线开单

### 2.1 问题

两台设备都离线、都在卖同一批货。如果设计成「共享一个库存数字」，两边各自扣减，收盘后必然对不上，还得解决谁对谁错。

### 2.2 解法：不做实时同步，做「标准流水 + 收盘并集合并」

三条原则：

1. **每台设备只写自己的流水**，主键用 UUID（离线生成，两台设备不可能撞车）。
2. **库存和毛利都是「算出来的」，不是「存着的」**：库存 = 进货 − 销售 ± 调整。
3. **合并 = 三张流水表按 UUID 取并集**，重复的自动丢弃。

结论：**永远不需要解决写冲突**——因为两台设备从来不会去改同一个数。

代价（明说）：摊位上你俩看到的「还剩多少」是**本地估算**，可能比真实多 → 极端情况会轻微超卖。恢复网络自动合并后立刻能发现，补货/换货即可。这比「两边都改同一个库存然后打架」好一百倍。

### 2.3 云同步（2026-11-08 追加，默认开启）

- 本地写入先落 Dexie + `outbox` 发件箱；联网后按 UUID 推送到 Supabase，再增量拉取对方记录。
- 触发时机：打开 / 回前台 / 网络恢复 / 每成交一单（约 0.7 秒）/ 每 10 秒。
- 销售流水按 UUID 并集，只增不改；商品与设置按 `updatedAt` 后写胜；删除用墓碑。
- 配置已内置（`src/db/syncDefaults.ts`），两台手机打开即同一账本；可在设置里换成自己的同步码。

### 2.4 手动导出/导入（保留为备份）

- 一方「导出备份」→ 微信发送 → 另一方「导入合并」；合并前有预览和“先导出本机备份”，结果页可撤销。
- 云同步正常时不需要手动合并，它只是兜底和换机恢复。

### 2.5 合并后的成本怎么算

**FIFO 重放**：进货批次按日期先进先出，销售出库按时间顺序取批次成本。两台设备的单子合到一起后按时间重排，成本才算得准。所以毛利是**报表时计算的**，不是开单时固化。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 形态 | **PWA**（浏览器装到桌面，全屏、离线） | 手机+平板一套代码，不用装商店、不要钱、不要审核 |
| 前端 | React 18 + TypeScript + Vite | 开发快、生态全、你后续好维护 |
| 界面 | **GlassKit 1.40**（iOS 26 Liquid Glass，纯 CSS，MIT） | 38 个现成组件、深色/浅色、液滴选中动画，不自己造轮子 |
| 图标 | lucide-react | 统一线性图标，和玻璃风格匹配 |
| 数据 | Dexie.js（IndexedDB） | 离线存储、事务、查询都够用 |
| 自定义样式 | 少量应用层 CSS（用 GlassKit 的令牌） | 只写玻璃组件没有的布局，不重复造组件 |
| 离线 | vite-plugin-pwa | Service Worker 预缓存，断网刷新也能开 |
| 云同步 | Supabase（PostgREST + RLS） | 免费、无需自建服务器；publishable key + 内置同步码，开箱即用 |
| 打包（可选） | Capacitor → APK | 安卓可打成原生包，规避浏览器清缓存风险 |
| 账本 | 本地 Dexie 为主 + 云同步（Supabase Postgres） | 离线可用；云端一份主账，联网自动推拉；免费额度够用 |

> 界面走 GlassKit 的玻璃设计语言：深色极光背景 + 半透明玻璃卡片 + 悬浮胶囊 Tab Bar（带液滴选中动画），深/浅色可在右上角一键切换。

**为什么不是别的**：
- 桌面程序（SQLite + WebView2）：手机/平板用不了，直接排除。
- 微信小程序：要资质、要服务器、要审核，春节前不划算。
- Excel：解决不了合并、日结和毛利。

**已知风险**：iOS 上若只是普通浏览器标签页，长期不打开可能被系统清存储。装到主屏幕可缓解，最稳是**每天收盘一键导出备份**（备份文件存微信收藏即可）。

## 4. 数据模型（IndexedDB / Dexie）

> 约定：**钱用整数「分」**，**数量用整数「基本单位」**（个/挂/支），时间存 ISO 字符串，所有表带 `id`(uuid)、`deviceId`、`createdAt`。

### products 商品
| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | UUID |
| name | string | 商品名 |
| category | '炮' \| '烟花' \| '儿童' \| '组合' | 分类（对应开单大按钮） |
| unitBase | string | 基本单位：个/挂/支 |
| boxQty | number | 1 箱 = N 个（拆零换算；不拆零的填 0） |
| priceList | number | 零售标价（分/基本单位） |
| negotiable | boolean | 是否允许砍价 |
| archived | boolean | 停用 |
| sortOrder | number | 分类内排序 |

### batches 进货批次（= 纸质送货单上的一行）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | UUID |
| productId | string | |
| batchNo | string | 批号（可空，金蝶 `FLot` 语义） |
| produceDate | string | 生产日期（可空） |
| expiryDate | string | 有效期至（可空，用于临期预警） |
| qtyBase | number | 进货数量（基本单位） |
| unitCostFen | number | 进货单价（分/基本单位） |
| supplier | string | 厂家/供货商 |
| receivedAt | string | 进货日期 |

### salesOrders 销售单头
| id | deviceId | operator | createdAt | payMethod('cash'\|'wechat'\|'alipay') | totalFen | note |

### saleLines 销售明细
| id | orderId | productId | qtyBase | unit('box'\|'base') | listUnitPriceFen | unitPriceFen | amountFen | discountFen |

> `discountFen = (listUnitPriceFen − unitPriceFen) × 数量`，砍价留痕就靠它。

### adjustments 调整（退货/盘亏/补正）
| id | productId | qtyBase(正负) | type('return'\|'loss'\|'correction') | reason | createdAt |

### settings 设置
| key | value | 例：deviceName / operatorA / operatorB / expiryWarnDays |

### 派生计算（不落库）
```
库存(商品) = Σ batches.qtyBase − Σ saleLines.qtyBase + Σ adjustments.qtyBase
金额       = priceFen / 100（显示时才转）
FIFO 成本  = 按批次日期先进先出重放 {batches, saleLines}
```

### outbox / 云端同步（2026-11-08 追加）
- `outbox`（IndexedDB）：每次本地写入登记 `{kind, recordId, op, queuedAt}`，推送成功即删。
- 云端 `yh_records`（Supabase）：`id, record_id, ledger, kind, data, updated_at, device_id, deleted`；RLS 用请求头 `x-ledger-key` 校验同步码。
- 拉取：`updated_at > lastPull` 增量；冲突规则见 2.3。

## 5. 页面与流程（v1 共 7 页）

1. **开单**（首页）：分类大按钮 → 点商品加购物车 → 数量按箱/个切换 → 结算（现金/微信/支付宝）→ 改价按钮（留痕）。
2. **商品**：列表 + 新增/编辑（名称、分类、单位、1 箱=几个、标价、能否砍价）。
3. **进货**：选商品 → 数量/单价/批号/生产日期/有效期 → 保存并继续下一条（纸质单照录）。
4. **库存**：按商品汇总（几箱几件）+ 批次明细 + 临期高亮（过期红、7 天内黄）。
5. **报表**：日报/日结（销售额、现金、电子收、成本、毛利、砍价让利）+ 单品毛利 + 年后总账。
6. **历史**：销售记录列表，可退货（写 adjustment）。
7. **设置/同步**：设备名、操作人、云同步状态、导出备份、导入合并、清空数据。
