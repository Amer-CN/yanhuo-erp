> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复 2026-11-13 审计发现的错单、误清、恢复污染、同步丢改动和跨页漏明细问题，完成可复核的发布门禁与两台真机验收。

## 1. 策略选择

| 路径 | 好处 | 代价 | 本轮决定 |
|---|---|---|---|
| 只隐藏危险按钮 | 快速降低误操作 | 丢单/跨页等根因仍在 | 仅可作临时止血，不作为稳定版终态 |
| 分批修复 + 增量回归 + 单独协议迁移 | 变更可二分、证据明确、保住既有体验 | 需要多个独立提交 | **采用** |
| 重新设计后端/状态管理并升级全套依赖 | 可统一架构 | 风险面最大，难知道修了什么又引入什么 | 本轮不做 |

业务决策采用以下保守默认值，不把这些技术问题转交用户裁决：

- 编辑已有订单只提供“保存修改”，保存后回列表；“保存并记下一单”仅用于新单。补记可继续补同一目标场次，文案明确“保存并继续补记”。
- 建商品返回原 editor 模式、orderId/sessionId、原草稿，不能无条件跳新单。
- 危险操作一旦开始提交，确认、取消、Esc、遮罩和系统返回全部锁定，直到明确成功/失败。取消只在提交前承诺保留数据。
- **撤销合并恢复本机，不清整个云账本。** 导入已传播时，整库反向覆盖不是安全撤销；恢复本地后暂停同步并明确提示“云端未回滚”。重新连接先预览差异，不能一键将恢复快照整库标脏。目标是保留各端唯一数据，不承诺自动撤销已经广播给其他设备的每一个改动。
- 备份恢复先隔离同步，再原子替换本机数据、清旧队列/诊断，暂停状态跨重启保持。恢复后的单据不能因旧队列残留变成云端墓碑。
- H3 撤销以整张订单为单位，包括单头、明细和新业务时间；快照不完整或本机之后又改过时不给虚假“撤销成功”，提示到记录页核对。
- 云端清空改为单个幂等 RPC 事务；没有部署该能力时不回退到 PATCH + POST 两请求方案，也不清本机来假装两端都成功。

## 6. 发布与回滚

1. 本地分支通过 A–E，独立复核无 P1；保留每批提交可回滚。
2. 两台设备先导出备份；核对生产迁移现状（列/约束/策略/RPC），不用文档旧说法当证据。
3. 按 B07 的阶段一→兼容前端→两端升级→阶段二顺序发布；没有生产控制台授权时只交付迁移脚本和人工步骤。
4. 核对 GitHub Actions headSha 与线上资源；手机 PWA 也必须显示同一 build 标识（F04 添加）。
5. 先在独立账本真机演练，再进行真实营业；记录日期、build、设备、场景、结果。
6. 普通前端错误用 git revert 本任务提交；不 reset 历史、不把数据库版本手工降回旧值。
7. **复合账本主键落地后不能回滚到使用 `on_conflict=id` 的旧前端。** 需要保留协议兼容的上一个前端构建。阶段二前可取消迁移；阶段二后优先前向修复。
8. 多 ledger 已出现同 id 时，恢复全表 `id` 唯一约束会失败，禁止靠删账本/删冲突行解决回滚。
9. 清空/恢复类失败先停同步、导出现场；不执行“再清一次整个账本”作为通用补救。

官方说明用于设计依据，不取代项目的红绿回归、实际SQL/RLS和真机证据；本轮没有执行这些外部页面中的命令。
