# 审计账本与同步合同修复设计

## 意图

降低订单、恢复和真实同步测试跨文件规则不一致造成的数据风险。只修本轮已复现或有直接合同证据的四项：恢复期间陈旧业务写、备份合并订单/明细分叉、批量报表缺省值不一致、真实 E2E 清理沿用旧协议。

## 目标

- 一次业务命令若在恢复开始前读取了数据，恢复换代后提交时必须拒绝；普通暂停仍允许本地离线开单。
- 订单在备份中作为“订单头 + 完整明细 manifest + 明细集合”处理，不按独立行无条件并集。
- 只有完整且通过金额校验的订单组可自动替换；使用旧格式或同版本内容冲突时保留本机并向用户显示计数。
- 单场、批量场次汇总对缺失 `discountFen` 都按 0 处理，批量路径继续保持 O(N)。
- 真实 E2E 每轮使用隔离账本，以 `yh_clear_ledger` 和 operationId 清理；清理失败必须令测试失败。
- 以回归测试为先，最终运行全部单元、Python、安全/静态检查和构建门禁。

## 非目标

- 不重新设计 Session closed/open 的跨设备合并规则，不改变快照权威性。
- 不重写同步状态机、Context、页面路由或整个 BackupFile schema。
- 不运行生产 SQL、不访问真实业务账本、不 push、不 deploy。
- 不为了这批修复做全仓文件拆分、格式化或依赖升级。

## 方案

1. **整体重构**：将业务实体改为事件溯源/版本化快照，重写备份和同步。语义更完整，但改动面和数据迁移风险远超本轮复现问题，不采用。
2. **目标合同加固（采用）**：在写入事务中校验命令开始时的 generation；备份合并只对具备完整 manifest 的订单组应用版本比较；修正批量计算默认值；真实测试账本改为每轮隔离并调用现有幂等清理 RPC。保留既有领域模型和测试栈。
3. **仅补测试/文档**：能记录风险但不能阻止旧业务写回或订单金额失真，不满足修复目标。

## 关键行为

### 恢复换代与业务写

- `captureWriteGeneration()` 在可能发生外部读取之前读取同步控制行；若当前处于 maintenance，拒绝启动。
- 每个读后写业务命令携带捕获的 generation，写事务必须包含 `syncMeta` 并原子检查：maintenance 为真或 generation 不匹配时不写业务表、不入队。
- 当前 pause 不阻断本机业务写；只有维护窗口和已换代的旧命令被拒绝。
- 简单单事务的 `ensureDeviceId` / `clearAllData` 继续用事务内读写，不额外引入 fence。

### 订单备份合并

- 订单带 `lineIds` 时，它是完整 manifest：ID 唯一，必须与备份中该订单的行集合完全一致，行金额之和必须等于 `totalFen`；不满足则在写入前拒绝导入。
- 新订单整体导入。
- 同 ID 的完整订单只比较一次版本（`updatedAt`，缺失时回退 `createdAt`）。较新的完整订单替换头与全部明细；不新于本机的版本保留本机。
- 同时间但内容不同，或同 ID 的来件缺少 manifest，均不单独追加其明细；保留本机并计为冲突。旧备份中没有 manifest 的新订单仍按旧兼容行为导入。
- 替换订单时，旧本机多余行从本地删除并登记 outbox delete，选中新行登记 upsert，与订单头同事务提交。
- 合并结果和 UI 明示更新、删除与冲突计数；其他流水表维持现有只增语义。

### 汇总与真实 E2E

- 批量场次聚合将缺失的 `discountFen` 当 0，与单场实现一致。
- 真实 E2E 的配置账本只作为 test namespace；每次启动派生唯一 run ledger。收尾只向 `/rest/v1/rpc/yh_clear_ledger` 发送新 operationId，并核对 receipt 的 operationId；网络/HTTP/无效回执均使脚本失败。
- 默认 CI 仍只运行本地 mock；真实 PostgREST/RLS 测试仍使用既有独立协议脚本，不接生产环境。

## 验收与风险

- fake-indexeddb 回归必须先复现：旧 updateRecord 在恢复完成后不能重新出现订单或 outbox。
- merge 回归覆盖完整较新版本替换、较旧版本保留、同时间冲突保留、旧 manifest 缺失兼容、错误 manifest 原子拒绝，以及相应 outbox 操作。
- 批量/单场对 legacy line 逐字段相等，`discountFen` 有限且为 0。
- Python 单测验证每轮 ledger 隔离、RPC 请求合同、receipt mismatch 和 cleanup failure。
- 现有 336 个 Vitest 基线已通过。环境缺失的真实云端/真机验收记为未执行，不由本轮单测替代。

主要风险是旧备份缺少 lineIds，故不得猜测其订单组完整性或静默拼接明细；generation 检查必须发生在同一个包含 syncMeta 的读写事务中。
