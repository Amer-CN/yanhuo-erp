### T02 · 本地自动备份（收摊后 + 手动 + 保留 3 份）

| 字段 | 内容 |
|---|---|
| 对应债务 | TD-08（P0，Major） |
| 目标 | 把「记得导出」变成系统动作：收摊成功后自动落一份本地快照，并提供恢复入口 |
| 前置 | 无 |
| 预估 | 1–2 人日 |
| 改动文件 | 新增 `src/db/backup.ts`、`src/ui/pages/SettingsPage.tsx`、`src/App.tsx`（收摊成功后调用）、`tests/backup.test.ts`、`package.json`（若需 `fake-indexeddb`） |
| 禁止 | 不把快照写进主库 `yanhuo-erp`（会触发 schema 版本耦合）；不动 `clearAllData` 行为 |

**设计**

- 备份库使用**独立的 Dexie 实例**，与主库分离，避免主库升级事务干扰：
  ```ts
  // src/db/backup.ts
  const backupDb = new Dexie('yanhuo-erp-backup');
  backupDb.version(1).stores({ snapshots: '++id, at, reason' });
  ```
- 快照条目：`{ id?: number; at: string; reason: 'close' | 'manual' | 'pre-migrate'; schemaVersion: number; deviceId: string; file: BackupFile }`，直接复用 `merge.ts` 的 `exportBackup()` / `BackupFile`。
- 保留策略：`prune()` 保留最近 3 份「不同日期」的快照 + 最近 1 份 `pre-migrate`；其余删除。
- 恢复：`restoreSnapshot(id)` 调用 `replaceAll(file)`；**恢复后默认不自动推送云端**（避免旧快照覆盖较新的云端数据）。恢复前二次确认，恢复后提示「云同步已暂停，确认无误后在设置页重新开启」，并写入 `localStorage['yh-sync-disabled']='1'`。

**步骤**

1. 新建 `src/db/backup.ts`，导出：`createSnapshot(reason)`、`listSnapshots()`、`restoreSnapshot(id)`、`pruneSnapshots()`、`latestSnapshot()`。
2. 在 `App.tsx` 的收摊成功分支调用 `createSnapshot('close')`（失败只 toast 警告，**不得**阻断收摊流程）。定位方式：搜索 `closeSession(` 与 `setCloseDone`，在结账成功、`setCloseDone` 之后插入。
3. `SettingsPage.tsx` 增加「本地备份」区块：最近 3 份（时间/单数/销售额）、「立即备份」「恢复」「导出」三个按钮；恢复用现有 `ConfirmSheet` 二次确认。
4. 写 `tests/backup.test.ts`（用 `fake-indexeddb/auto`）：造 2 单 → snapshot → 清主库 → restore → 断言订单数、销售额、商品数一致；断言 prune 后只剩 ≤4 条。
5. 添加 `fake-indexeddb` 到 devDependencies（若 T08 尚未安装）。

**验收**

```powershell
pnpm test -- backup        # 期望：备份/恢复/裁剪 3 个用例通过
pnpm build
# 手动：pnpm dev → 记 1 单 → 收摊 → 设置页看到 1 条备份 → 恢复 → 金额一致
```

**回滚**：删除 `backup.ts` 与调用点；备份库 `yanhuo-erp-backup` 可保留（不影响主流程）。

**设计要点（必须按此实现，避免触发升级）**

- 快照必须在 **Dexie 首次打开主库之前** 完成。`App.tsx` 的 boot effect 中，当前顺序是 `ensureDeviceId()` 最先——要插到它前面。

- 仅当 `oldVersion < 3` 或 `migrateSessions` 将要执行（`settings.sessionsMigrated !== 'yes'` 且存在 `sessionId` 为空的订单）时创建 `pre-migrate` 快照。

3. `App.tsx` boot effect 第一行 `await snapshotBeforeOpen()`；失败不阻断启动（`console` 不输出，用 `setMigrateError` 之外的静默处理，避免打扰摊主）。

### T09 · 同步冲突：业务时间戳 + 冲突留痕 + 退避

| 字段 | 内容 |
|---|---|
| 对应债务 | TD-02（P1，Major） |
| 目标 | 修复「远端已存在且 voided 相同 → 编辑永不同步」的缺陷；冲突不再静默覆盖；失败有退避 |
| 前置 | T08（有测试基建）、T07（冲突前可回滚） |
| 预估 | 3–5 人日 |
| 改动文件 | `src/db/types.ts`、`src/db/repo.ts`、`src/db/db.ts`（v4）、`src/db/sync.ts`、`src/ui/useSync.ts`、`supabase/schema.sql`（新增列，人工执行）、新增 `supabase/migrations/*.sql`、`tests/sync-resolve.test.ts` |
| 禁止 | 不在没有人工执行 SQL 的情况下假设 `record_updated_at` 已存在；不删除旧 `updated_at` 字段；不清空 `outbox` |

**已确认的缺陷（先写一个失败测试再修）**

`sync.ts` 的 `case 'order'` 当前逻辑：
```ts
if (!cur || Boolean((cur as SalesOrder).voided) !== Boolean(remote.voided)) {
  putRow('order', ...)
}
```
→ 如果本地已有该单且作废状态相同，**远端的编辑/改价/改数量永远不会被应用**。这比「覆盖」更隐蔽。

**设计**

1. 数据模型：`SalesOrder`、`Batch`、`SaleLine`、`Adjustment` 增加可选 `updatedAt?: string`；所有写入与作废/恢复都写 `nowIso()`。旧数据读取时用 `updatedAt ?? createdAt ?? ''` 兜底。
2. 远端表增加 `record_updated_at bigint`（毫秒）：
   ```sql
   alter table public.yh_records add column if not exists record_updated_at bigint not null default 0;
   create index if not exists yh_records_ledger_record_updated
     on public.yh_records (ledger, record_updated_at);
   ```
   **这是人工步骤**（§7-B）：Agent 只提交迁移文件与代码，不执行 SQL。代码必须容忍列不存在：push 时若 PostgREST 返回 400 且错误码为 `PGRST204`（unknown column），自动降级为不发送该列并记录一次告警。
3. 决策函数（纯函数，放 `src/db/syncResolve.ts`，便于单测）：
   ```ts
   resolveRemote(kind, cur, remote): 'take-remote' | 'keep-local' | 'conflict'
   ```
   规则：`remote.recordUpdatedAt > localUpdatedAt` → take-remote；`<` → keep-local；相等或缺失 → 按 kind（order 比较 `voided`、session 用 `mergeSessionPair`、product 比较 `updatedAt`）。
4. 冲突留痕：Dexie v4 新增 `conflicts: '++id, at, kind, recordId'`；发生 `conflict` 时把两侧 JSON 写入，**本地保留**，并在设置页显示「待核对 N 条」。
5. 退避：`useSync.ts` 用 `backoffRef`，失败后延迟 `1s→2s→4s→…→60s`，成功后重置；轮询间隔保持 10s，但失败期间以退避为准。
6. 推送 `updated_at` 仍用推送时刻（作为增量水位），`record_updated_at` 用业务时间；`pull` 的 `gt` 水位继续用 `updated_at`。

**验收**

```powershell

pnpm test
pnpm build
python scripts/e2e-sync.py    # mock Supabase，双设备
```

手工验收（可选，需人工提供测试账本）：两台设备交替改同一单 → 设置页出现冲突 → 保留本地/远端均可。

**回滚**：代码 revert；云端新增列可保留（默认 0，不影响旧客户端）。

### T09b · 远端缺列时用 `data.updatedAt` 兜底（push 前补丁）

| 字段 | 内容 |
|---|---|
| 对应债务 | TD-02 残余风险 |
| 目标 | 在人工执行 `record_updated_at` 迁移前，远端编辑仍能被应用 |
| 前置 | T09 |
| 预估 | 0.2–0.5 人日 |
| 改动文件 | `src/db/syncResolve.ts`、`tests/sync-resolve.test.ts` |
| 背景 | 当前 `resolveRemote` 的 `remoteTime = Number(remoteRecordUpdatedAt) \|\| 0`；缺列时恒为 0，而本地 `businessTime(cur) > 0`，因此对已存在记录恒返回 `keep-local`——远端编辑在迁移执行前不会生效。 |

**实现**

```ts
const remoteTime = Number(remoteRecordUpdatedAt) || businessTime(remote);
```

保留原有「两端都无法判定 → keep-local」的保守策略。补两条用例：

- 远端 `record_updated_at = 0` 但 `data.updatedAt` 新于本地 → `take-remote`
- 远端 `record_updated_at = 0` 且 `data.updatedAt` 旧于本地 → `keep-local`

**验收**

```powershell
pnpm test -- sync-resolve
pnpm test:cov
pnpm build
```

手测（不需要云端）：让 mock 返回不带 `record_updated_at` 的行，确认远端编辑仍被应用。

- 类型：`feat|fix|test|ci|chore|docs|refactor`（不引入新类型）。
- 不把 `pnpm-lock.yaml` 与业务代码混在同一 commit（除 T10 的依赖批次）。

## 10. 全局 Definition of Done

一张任务卡只有同时满足以下条件才算完成：

1. 代码改动范围与任务卡一致，无顺手重构/格式化。
2. 任务卡列出的验收命令全部通过，输出摘要写入 `docs/07`。
3. 新增/修改的导出函数有类型；`tsc --noEmit` 无错误。
4. 涉及数据写入的改动有对应单测；涉及 UI 的改动在 390px 宽度手测一次。
5. 不引入新的 `any`、`@ts-ignore`、`console.*`（测试除外）。
6. 有回滚说明；涉及 schema 的附回滚 SQL。
7. 没有修改真实账本/真实云端数据。

## 11. 失败与升级路径

| 情况 | 处理 |
|---|---|
| 验收命令因环境失败（缺 Chromium、端口占用） | 记录错误原文，换用 `pnpm preview` + 4173 重试；连续 2 次失败则中止并报告 |
| 发现计划与代码事实不符（如某函数已被引用） | 停止执行该卡，在 `docs/07` 记录证据与建议，等待确认；不要自行改方案 |
| 单测暴露真实业务 bug | 先写最小失败用例 + 修复，commit 信息注明 `fix`，并在记录中标注「计划外修复」 |
| 需要改云端 schema | 只写迁移文件，标记 blocked，等待人工执行 |
| 时间超出预估 2 倍 | 停止扩展范围，交付已完成部分并报告剩余工作 |
