## P2 · push 与 CI 验证（**必须等用户明确说「可以 push」**，0.2 人日）

```text
任务：P2（发布，需用户明确授权）

前置（缺一不可）：
1. P1 全绿，docs/07 有发布检查表。
2. 用户已明确说「可以 push」。
3. 用户已确认两台设备各导出过备份。
4. 用户已知晓：push 会触发 GitHub Pages 部署，线上立即更新。

步骤：
1. 记录发布前状态：
   git rev-parse HEAD
   git status --short            # 期望仅 .opencode/
   git log --oneline origin/main..HEAD | Measure-Object | Select-Object -ExpandProperty Count
2. push：
   git push origin main
3. 等待并验证 CI（二选一）：
   gh run list --limit 5
   gh run watch <run-id> --exit-status
   或打开 GitHub Actions 页面确认：
   - deploy.yml：build + Unit tests + Lint + Deploy 全绿
   - e2e.yml：check-default-sync / e2e-smoke / e2e-sync / e2e-offline 全绿
4. 验证线上：
   Invoke-WebRequest https://amer-cn.github.io/yanhuo-erp/ -UseBasicParsing | Select-Object StatusCode
   期望：200；再打开一次确认首页可渲染（不登录、不写数据）。
5. 回填：
   - docs/05 的 TD-04 状态改为「已关闭（2026-11-xx，CI run <id>）」
   - docs/07 追加一行：push commit、两个 workflow 的 run id 与结论、线上状态码
   - 若 deploy 失败：记录失败 job 与日志摘要

禁止：
- 不用 git push --force
- 不在 CI 红的情况下继续改代码；先定位失败原因
- 不执行 Supabase SQL（仍属人工）
- 不改版本号 / 不打 tag（除非用户要求）

失败处理：
- e2e.yml 红：看是脚本选择器、超时还是真实回归；修复后新 commit，不 force push。
- deploy.yml 红：检查 pnpm version / Node 22 / build 产物路径；修复后重新 push。
- 线上 404/白屏：检查 base './'、Pages 源分支、dist 产物；必要时用上一版 commit 重新部署。
```
