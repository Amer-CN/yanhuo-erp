## 二、P0 — 会静默产生错误账本 / 静默丢数据（4 项）

### P0-1 拉取水位建立在「对方手机时钟」上，时钟偏快的一端会永久漏拉（来源：后端 H-1；测试 H3 与其同源）

- **位置**：`src/db/sync.ts:362`（推送时 `updated_at: Date.now()`）、`src/db/sync.ts:654-675`（`buildPullParams`）、`src/db/sync.ts:762-781`（`pull`）、`supabase/schema.sql:10`
- **机理**：云端 `updated_at` 由推送端时钟生成，拉取条件 `updated_at > 本地水位`，而水位同样来自客户端时间戳（**包含本机自己推上去的行**）。设 B 时钟比 A 快 Δ，B 推完水位就跳到了「未来时间」，A 在这 Δ 窗口内推的行**永远不会被 B 拉到**——行的时间戳是固定的，水位只会上涨。
- **后果**：Δ=2s 就可能每次同步静默丢一单；Δ 为小时/天（手改系统时间、RTC 无电、时区误设）时两端账本长期完全不一致，而 `syncNow` 返回成功、设置页照常显示「已连接」，`yh-sync-warn` 也不写。唯一自愈路径是「清空标记」全量重放，正常使用不会发生。
- **建议（按代价排序）**：
  1. 过渡方案（不改库、当天可做）：`pull` 起点回退 `OVERLAP_MS`（如 5 分钟）做重叠窗口重放，重复应用已被 `applyRemoteBatch` 幂等吸收；
  2. 正解：`updated_at` 改由服务端生成（列 `default` 或 `BEFORE INSERT OR UPDATE` 触发器 `extract(epoch from now())*1000`），客户端不再写该列；
  3. 兜底：每日首次启动或每 N 轮同步做一次 `cursor = 0` 全量重放；
  4. 可观测：同步面板显示「远端行数 vs 本地行数」偏差，让不一致能被人看见。

### P0-2 判定「本地较新」后从不回推云端，云端可能长期停在旧版本（来源：后端 M-2）

- **位置**：`src/db/sync.ts:513-523`（`keep-local` 与 `conflict` 分支均只 `continue`）、`src/db/syncResolve.ts:56-75`
- **机理**：云端那行已被对方用更旧的版本覆盖（upsert by id，最后推送者赢）；本机判「本地更新」后**既不改本地也不重新入队**，于是没有任何一方把正确版本推回云端。
- **后果**：换手机 / 重装并从云端恢复时拿到被回退的数据——已作废的单复活、补记丢失、`summary` 金额回退。这是「云端作为备份」这一承诺的实质失效。
- **建议**：`keep-local` / `conflict` 时 `enqueue(kind, id)` 回推；用「仅当本地 `businessTime` 严格更大」作门槛，或对同一记录 30s 内最多回推一次，避免两端互推成环。

### P0-3 「业务写入」与「outbox 入队」不在同一事务（来源：后端 M-1）

- **位置**：`src/db/repo.ts:438-445`（`saveRecord`）；同一模式共 12 处：`:471-480`、`:493-500`、`:523-532`、`:554-555`、`:612-621`、`:171-172`、`:205-206`、`:95-96`、`:835-836`、`:30-33`、`:265-266`
- **机理**：先 `await db.transaction('rw', …)` 落账，**事务结束后**再 `await enqueue(...)`，两次独立事务不相邻。
- **后果**：① 入队抛错时记录已入库但**永不推送**，异常还会让 UI 报「保存失败」→ 摊主重录 → 同一单重复记账；② 两次 `await` 之间进程被杀，静默留下永不发送的记录，全仓没有补扫机制（`markAllDirty()` 只在手动导入/撤销合并后被调用）。
- **建议**：把 outbox 写入并入业务事务（`db.transaction('rw', [db.orders, db.lines, db.outbox], …)`）；做不到就先加启动期对账器，扫「本地有、outbox 无、且 `updatedAt > yh-sync-last-sync`」补入队。**注意**：`clearAllData` 里 `outbox.clear()` 必须最后执行（基线第十二节踩坑记录），别改坏这个顺序。

### P0-4 远端墓碑删除路径缺少 `SKIP_SETTINGS` 白名单，可删掉本机 `deviceId`（来源：后端 M-5）

- **位置**：`src/db/sync.ts:499-503`（`if (row.deleted) { … deleteRow(...) }`）对比 `src/db/sync.ts:534-541`（put 路径有 `SKIP_SETTINGS` 判断）
- **机理**：写入侧严格跳过 `deviceId / deviceName / sync-unknown-kinds`，删除侧完全不判断；任何 `kind='setting' && deleted=true` 的远端行都会 `bulkDelete` 掉这些键。当前仓库没有代码会 `enqueue('setting', key, 'delete')`，所以**暂时不可达**，但一旦出现（旧版本 bug、控制台误操作、持码者写入）就命中。
- **后果**：`deviceId` 被删后 `ensureDeviceId()` 生成新 UUID，`getOpenSession()`（`repo.ts:243-248`）与 `App.tsx:72-77` 都按 `deviceId` 过滤 → **本机正在进行的场次立刻「找不到」**，被迫新开场次，结账链路断裂。
- **建议**：删除分支加同样守卫；更彻底的做法是「设置永不同步删除」（对 `setting` 忽略 `deleted=true`）。**这一处同时被测试维度点为 H1（零覆盖），修完必须补用例锁死。**
