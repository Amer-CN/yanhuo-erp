# 人工发布检查表（本轮只编写，不执行）

适用：从稳定性修复候选升级已有账本。顺序固定：**两台先备份 → 独立协议验收 → 生产 prepare → 兼容前端发布 → 两台确认构建 → 人工 finalize → 真机测试账本演练 → 营业日对账**。

本轮未 push、不部署、不执行生产 SQL、不切换真实账本、不轮换凭据；本机独立loopback PostgreSQL/PostgREST协议验收已完成，并非“未做本地HTTP”。下列空框均须将来由获授权维护者据实际证据填写；任何本机成功都不能代勾生产或目标真机。协议正本和验收结果见[总方案](../superpowers/plans/2026-11-13-stability-repair.md)，使用与排障见[云同步设置](../03-云同步设置.md)及[运维手册](../08-运维手册.md)。

## 1. 两台先备份

- [ ] 两台设备均在场，记录当前 build、上次同步、待推送数量、订单/明细数和金额；没有把一次“连接成功”当全量已齐。
- [ ] 两台分别在“更多 → 设置与同步 → 导出备份”导出 JSON；复制到独立存储，记录文件名、时间、大小、SHA256。能解析 JSON，并在隔离环境打开核对商品/订单/明细/金额。
- [ ] 维护者保存迁移前云端备份及约束/索引/策略/函数权限清单，标注对应环境与日期。备份中凭据不进入公开文档。
- [ ] 备份期间暂停危险操作与发布；两端唯一数据均已有可恢复副本。

## 2. 独立协议验收

使用专用 loopback 测试 PostgreSQL/PostgREST；新库执行[新库正本](../../supabase/schema.sql)，旧库副本依序执行 [prepare](../../supabase/migrations/2026-11-13-stability-prepare.sql) 和 [finalize](../../supabase/migrations/2026-11-13-stability-finalize.sql)。owner 管建库/迁移；HTTP 使用独立 authenticator 登录并切 `anon`，不得以管理员或 BYPASSRLS 假验权限。

- [ ] URL 库名、预期库名和 `current_database()` 相同，且 `pg_db_role_setting` 中有数据库级 `yh.protocol_test_database=stability-2026-11-13` 标记。普通会话临时 SET 不算标记。
- [ ] 按[运维手册本地门禁](../08-运维手册.md#12-本轮候选的本地门禁与交付边界)执行全量检查，保存完整输出及 exit code，不降低阈值。

```powershell
# 这些变量只指向独立测试环境；值由维护者本地设置，勿放进发布记录。
python scripts/run-supabase-sql-test.py --database yh_stability_test
# psql 不在 PATH 时追加 --psql <便携 psql.exe 的绝对路径>
python scripts/e2e-supabase-protocol.py
```

- [ ] 真实 HTTP 证明 `(ledger,id)` 冲突目标、请求头/RLS、跨账本隔离、旧 epoch 拒绝、清空/写入并发、同 operationId 幂等、条件重连基线检查和丢响应重试保全后来数据。
- [ ] 实际制造错误账本/过期 epoch/变化基线并观察拒绝，再恢复合法请求通过；只看正常路径不算完成。
- [ ] 保存 schema 与迁移两条安装路径、事务回滚及独立连接竞争的证据。本机已有凭证可作为审查输入，不能替代发布候选实际版本核对。

## 3. 生产 prepare（人工执行）

- [ ] 备份已完成；维护者核对选中的生产项目，不把测试配置和生产配置混用。
- [ ] 人工执行 [prepare](../../supabase/migrations/2026-11-13-stability-prepare.sql)，保存 SQL Editor 输出和时间。已有账本不直接用新库脚本重建。
- [ ] 历史行数/业务汇总未丢失；显式补列 `record_updated_at`、`schema_version`、`clear_epoch`；旧 `PRIMARY KEY (id)` 仍在，复合唯一索引 `(ledger,id)` 已建立。
- [ ] RLS 已启用，业务表仅三条 `yh ledger read/write/update` 策略，anon 无 DELETE；state/receipt 无 anon 写权限；函数固定 search_path，能力响应符合 prepare 状态。
- [ ] schema cache 按脚本通知刷新。此时尚未 finalize，不切账本、不演练清云，不因“RPC 存在”推定最终能力可用。

## 4. 发布兼容前端（人工执行）

- [ ] 审定候选精确 commit、自动门禁与 14 组浏览器结果，保存可回滚的协议兼容前一构建。
- [ ] 获授权维护者按仓库流程整合并 push；main push 会自动测试与部署。检查 Actions 全部阻塞步骤成功，不能只看 deploy 步骤或 workflow 手动重跑的旧 sha。
- [ ] 记录 CI headSha、构建标识及发布资源；通过正常线上地址核对新版本，无缓存参数的用户入口也必须一致。

## 5. 两台确认同一构建

- [ ] 收摊后在两台“设置与同步 → 应用更新”确认更新；PWA 安装态与普通浏览器分别核对 build，记录设备 A/B 的构建标识。
- [ ] 两台均为审定的兼容构建，上次同步与待推送正常，订单/明细/金额核对一致。保留截屏时打码敏感信息。
- [ ] **两台都确认后才进入 finalize**；任一旧设备未确认则停在 prepare。

## 6. 生产 finalize（人工执行）

- [ ] 维护者人工执行 [finalize](../../supabase/migrations/2026-11-13-stability-finalize.sql)，保存真实输出。未知 FK、全局 UNIQUE、表达式/部分/INCLUDE/EXCLUDE 阻塞时停止审核，不加 CASCADE、不删冲突行。
- [ ] 实际主键为 `PRIMARY KEY (ledger,id)`，全局 id 唯一约束已按脚本处理；RLS/授权仍正确。
- [ ] `yh_sync_capabilities` 根据实际约束返回协议 2、`conflictTarget=ledger,id`、账本隔离及清云能力；条件重连 RPC 另需实际验证，不靠一个版本号证明全部能力。
- [ ] schema cache 已刷新，两台普通同步正常；此时仍不得在真实营业账本试清空。

## 7. 真机独立测试账本演练

下列操作只用专用测试账本/测试配置，先确认不是真实账本；切换须两台协调并保留原配置的私有恢复方式，不能临时轮换真实同步码代替测试。

- [ ] 两台同一 build，各录至少 10 单，覆盖多商品、整箱、赠品、改金额；核对订单集合、明细数、销量、收入、成本和支付分项一致。
- [ ] 一台断网至少 5 单，切微信/杀进程重开，联网后补发齐全无重复，仍能找到未保存草稿。
- [ ] 编辑已有单后另记新单；补记中建商品返回原场次；整单撤销对方改动，核对 orderId、目标 sessionId、完整明细与金额。
- [ ] 导入→撤销、恢复快照→重启→预览重连；另一台独有记录保留，无意外全账本墓碑；预览后另一端改动导致拒绝并要求重看。
- [ ] 清云只在测试账本：断网/超时后同 operationId 重试，清空后新记数据不会被重试再清；旧 epoch 写入明确拒绝。
- [ ] 安装态 PWA 更新、键盘开关、刘海安全区、返回键、嵌套弹层、横竖屏、浅/深色；实际设备有 iPhone 时包含 Safari/PWA。
- [ ] 保存每项设备/build/时间/输入/预期/实际/凭证。异常先导出现场，回到生产前恢复正确配置并双人核对。

## 8. 营业日对账与回滚边界

- [ ] 完整营业日记录订单/明细/库存和支付分项，对现金/微信/支付宝；两台同场次一致，金额与库存异常为零。
- [ ] 收摊两台各导出备份，至少一次在隔离环境恢复，核对金额、库存与明细。自动快照不能替代外部可恢复备份。
- [ ] 本表所有实测项与问题处理有证据后，才可称“目标真机验收完成”；营业日/恢复未做则继续 pending。

finalize 后不能回滚到仅使用 `on_conflict=id` 的旧前端。保留协议兼容构建并优先前向修复；多账本出现同 id 后不得靠删业务行恢复全表 id 唯一。清云/重连结果未知只重试原操作，先保留现场，不另起清空。前端回滚采用独立 revert，不改写历史；任何发布与回滚均由获授权维护者实际执行。
