# 移动端体验体检与优化方案（2026-11-11）

> 范围：`src/App.tsx`、`src/ui/**`（16 个文件逐个通读）+ `src/db/repo.ts` 写操作 + `src/db/sync.ts` 设置白名单 + GlassKit 1.40 的 `.glass-bg` / `.glass-toast` / `.glass-tab-bar-dock` 规则。
> 约束：只做诊断与方案，本轮不改 `src/**`。不引入新依赖、不换 UI 框架、不加全局状态库。
> 使用场景基线：两人两台手机、单手、戴手套、强光、嘈杂、断网也要开单。**任何改动都不得增加开单路径上的点击次数。**

---

## 摘要（先看这 6 行）

1. **输入法自动弹出有两个原因，改一个不够**：`ProductPicker.tsx:63` 的 `autoFocus` + `kit.tsx:327-330` 的「自动聚焦面板内第一个控件」（产品选择器的第一个控件正是搜索框）。
2. **顶栏其实写了 `sticky`，但没生效**：GlassKit 的 `.glass-bg { overflow-x: hidden }` 让它变成了滚动容器，`sticky` 吸附在一个永不滚动的祖先上 → 等于没吸。这是「返回按钮要滑到顶才能点」的真因，不是「没写固定」。
3. **「删除」不该新写真删除逻辑**：`deleteRecord()` 只允许 `session.status === 'open'`，而历史列表里绝大多数是已结账场次，直接调必抛 `SESSION_CLOSED`。**改文案 + 灰显 + 撤销**是唯一低成本正确解。
4. **滚动模型不要全站一刀切**：列表页（库存/销售记录/报表）改成内部滚动收益最大；**开单页必须留在文档滚动**，否则 iOS 软键盘一弹 `100dvh` 变化会把整单顶飞。
5. **操作人改成「本机编号」要顺手改一个同步白名单**：`operatorA/B` 不在 `SKIP_SETTINGS` 里（`sync.ts:61`），会把两台手机的操作人互相覆盖成一样。
6. **提示已有一套 `Toast`（fixed 浮层，不占位）**，问题不在缺组件，而在用错了地方：7 处本该用 Toast 的一次性提示写成了占位横幅。

### 诉求 1 · 点「添加商品」时输入法自动弹出

**现状**

`src/ui/ProductPicker.tsx:56-64`
```tsx
<input
  className="glass-input"
  type="search"
  placeholder="搜商品名"
  aria-label="搜商品名"
  value={q}
  onChange={(e) => setQ(e.target.value)}
  autoFocus          // ← 根因 A
/>
```
`src/ui/kit.tsx:320-330`
```tsx
const focusable = () => Array.from(panelRef.current?.querySelectorAll<HTMLElement>(
  'button:not([disabled]), [href], input:not([disabled]), select:not([disabled]), textarea:not([disabled]), [tabindex]:not([tabindex="-1"])'
) ?? []);
const items = focusable();
// 优先聚焦内容区第一个控件（如搜索框），关闭按钮放最后兜底
const first = items.find((el) => !el.classList.contains('glass-sheet__close')) ?? items[0];
(first ?? panelRef.current)?.focus({ preventScroll: true });   // ← 根因 B
```

**根因**（两个，缺一不可地都要改）

- A. `autoFocus` 是 React 的挂载即聚焦，Android Chrome / iOS 都会拉键盘。
- B. `Sheet` 挂载后无条件把焦点给「面板内第一个非关闭按钮的可聚焦元素」。`ProductPicker` 的 DOM 顺序是 `关闭按钮 → 搜索框 → 分类 chip → 商品按钮 → 底部完成按钮`，所以第一个非关闭控件 = 搜索框。**即使删掉 `autoFocus`，B 仍会把键盘拉起来**。B 是 2026-11-08 为无障碍焦点陷阱加的，不能直接删。

**建议改法**

1. `ProductPicker.tsx:63` 删掉 `autoFocus` 一行。
2. `kit.tsx` 的 `Sheet` 增加一个可选 prop，默认行为不变（不破坏其它 7 处调用）：
   ```tsx
   initialFocus?: 'first' | 'panel'   // 默认 'first'
   ```
   在 `:329-330` 改为：
   ```tsx
   const target = initialFocus === 'panel'
     ? panelRef.current
     : (items.find((el) => !el.classList.contains('glass-sheet__close')) ?? items[0] ?? panelRef.current);
   target?.focus({ preventScroll: true });
   ```
   `initialFocus` 要跟 `focusable()` 一样放进 `useEffect([])` 的闭包（不需要随渲染更新，它是挂载期常量）。
3. `ProductPicker.tsx:43` 调用处加 `initialFocus="panel"`。
   ``.glass-sheet` 已有 `tabIndex={-1}`（`kit.tsx:390`），聚焦面板本身不会拉键盘，同时保留 `aria-modal` 与焦点陷阱、屏幕阅读器仍会播报对话框标题。
4. 顺带确认：`ProductFormModal` 的 `autoFocus`（`kit.tsx:539`）**保留**——用户点「新建商品」就是要打字，那里弹键盘是对的。

**涉及文件**：`src/ui/ProductPicker.tsx`、`src/ui/kit.tsx`

**风险**：低。唯一副作用是打开选择器后焦点落在面板上，键盘用户按 Tab 会先到关闭按钮而不是搜索框——可在 `initialFocus="panel"` 时给搜索框加 `aria-describedby` 提示「按 Tab 搜索」，或直接接受（该页主交互是点商品，不是打字）。

### 诉求 3 · 返回按钮要滑到页面顶部才能点

**现状**

- 主页壳顶栏：`AppShell.tsx:114-134`，返回按钮在 `<header className="glass-nav app-nav">` 里（`:116-119`）。
- 样式：`styles.css:50-65`
  ```css
  .app-nav {
    position: sticky;      /* 写了 */
    top: 0;
    z-index: var(--yh-z-nav);
    ...
  }
  ```
- 开单页顶栏：`record.css:90-106`
  ```css
  .record-top {
    position: sticky;      /* 也写了 */
    top: 0;
    z-index: var(--yh-z-nav);
    ...
  }
  ```
- 但 GlassKit 的容器上有这一条（`node_modules/@jungherz-de/glasskit/glasskit.css`，`.glass-bg` 定义）：
  ```css
  .glass-bg { ... position: relative; min-height: 100vh; overflow-x: hidden; isolation: isolate; }
  ```
  DOM 层级：`div.glass-bg > div.app-shell > header.app-nav`（`AppShell.tsx:641-651`）。

**根因**（精确结论）

`overflow-x: hidden` 会让 `overflow-y` 的计算值变成 `auto` → **`.glass-bg` 成为一个滚动容器**（scroll container）。`position: sticky` 的吸附基准是「最近的滚动祖先把它的 scrollport」，于是 `.app-nav` / `.record-top` 吸附在 `.glass-bg` 上；而 `.glass-bg` 只有 `min-height`，高度随内容长，**它自己永远不滚**——真正滚动的是 `document`。结果就是：`sticky` 语法正确、行为失效，顶栏跟着页面一起滚走。

这解释了为什么代码里明明写了 `sticky` 却还是「要滑到顶部才能点返回」，也解释了为什么开单页（`.record-top`）尤其明显——开单页上一旦加了 3~5 行商品，页面就滚起来了，返回键直接滚出屏幕。

**建议改法（最小改动，先止血）**

`styles.css` 加一条覆盖（不改 node_modules）：
```css
/* GlassKit 的 overflow-x:hidden 会把 .glass-bg 变成滚动容器，使 sticky 失效 */
.glass-bg {
  overflow-x: clip;   /* clip 不创建滚动容器；Safari 16+ / Chrome 90+ */
}
```
一行即可让 `sticky` 复活。`overflow-x: clip` 的兼容兜底（如需覆盖 iOS 15）：
```css
@supports not (overflow: clip) {
  .glass-bg { overflow-x: hidden; }
}
```
（兜底等于维持现状，不会更差。）

**彻底方案**见 **第二节 C**（顶栏改为固定网格行，`sticky` 都不需要）。

**涉及文件**：`src/styles.css`（一行）；彻底方案另涉 `record.css`、`AppShell.tsx`、`kit.tsx`

**风险**：低。`overflow-x: clip` 不会裁剪 `position: fixed` 的子元素（`.checkout-dock`、`.record-actions`、`.glass-toast` 都靠 fixed），`hidden` 也不裁 fixed，但 `clip` 语义更干净。注意：**不要**改成 `overflow: visible`，因为 `::before` 极光斑会横向溢出产生横向滚动条。

同时删除/覆盖 `.prod-btn` 的 `flex-direction: column` 与 `.prod-btn__stock { margin-top: auto }`（后者在 grid 下无意义）。
`@media (min-width: 520px)` 的 3 列规则（`styles.css:227-231`）要一并改成 `repeat(2, ...)`，否则平板又变回卡片网格。

### 诉求 5 · 操作人：设成 001/002，且不要每单都选

**现状**

`src/App.tsx:49-52`
```tsx
const operators = useMemo(
  () => [settings[SETTING_KEYS.operatorA] ?? '我', settings[SETTING_KEYS.operatorB] ?? '老婆'],
  [settings]
);
```
`SettingsPage.tsx:137-138`、`:158-175`：两个自由文本输入「操作人 A / 操作人 B」，`onBlur` 落库。
`RecordEditor.tsx:225-243`：每单一个「操作人」分段控件，默认 `operators[0]`（`useRecordDraft.ts:82`）。
`sync.ts:61`：
```ts
const SKIP_SETTINGS = new Set<string>(['deviceId', 'deviceName', UNKNOWN_KINDS_KEY]);
```
→ `operatorA/B` **不在**白名单里，会随云同步推到另一台手机。

**根因**（三个独立问题，必须一起解决）

1. **数据模型错了**：现在建模的是「一个账本有两个人」，而真实情况是「**一台手机 = 一个人**」。所以每单都要选。
2. **同步方向错了**：`operatorA/B` 全量同步，手机 B 改了 B 的名字会把手机 A 的也改掉；两台手机的「A/B」根本不是同一个概念。
3. **措辞错了**：「我 / 老婆」是家庭称谓，用户要的是工号。

**建议改法**

1. 新增 per-device 设置键（`src/db/types.ts:155-167`）：
   ```ts
   operatorSelf: 'operatorSelf',   // 本机操作人编号，如 '001'
   ```
2. **加进 `SKIP_SETTINGS`**（`sync.ts:61`）：
   ```ts
   const SKIP_SETTINGS = new Set<string>(['deviceId', 'deviceName', 'operatorSelf', UNKNOWN_KINDS_KEY]);
   ```
   > 这一步是**硬前提**。漏了它，两台手机的编号会互相覆盖，用户会看到「我明明设的 001，怎么变成 002 了」。
3. `App.tsx:49-52` 改为：
   ```tsx
   const operators = useMemo(() => {
     const self = settings[SETTING_KEYS.operatorSelf]?.trim();
     return [self || settings[SETTING_KEYS.deviceName] || '本机'];
   }, [settings]);
   ```
   `operators` 的**类型与所有消费点保持不变**（数组），只是长度恒为 1 —— `CloseSessionFlow`、`useRecordDraft` 的 `operators[0]` 全部零改动。
4. `RecordEditor.tsx:225-243` 整块「操作人」分段控件**删除**。单操作人时是纯噪声，还占 ~52px 垂直空间（正好补给诉求 4/8 的密度）。
5. `SettingsPage.tsx:158-175` 改成「本机操作人编号」单输入 + 说明：
   - label：「本机操作人编号」
   - hint：「这台手机记账时记在谁名下。另一台手机设成 002。只影响本机，不会同步。」
   - 用 `inputMode="numeric"` + `maxLength={3}`，`onBlur` 落库。
   - 旧的 `operatorA/B` **保留读**（老数据仍能在历史里正常显示），但设置页不再暴露，避免用户以为还要填两个。
6. 历史/报表里 `order.operator` 是字符串快照，老单显示「我/老婆」，新单显示「001」——**可接受且无需迁移**。若想统一，可在 `ReportPage` 做展示层映射（不建议动 DB）。

**涉及文件**：`src/db/types.ts`、`src/db/sync.ts`、`src/App.tsx`、`src/ui/pages/SettingsPage.tsx`、`src/ui/RecordEditor.tsx`

**风险**：中。
- `sync.ts` 的 `SKIP_SETTINGS` 改动必须补一条测试（`tests/sync-inbound.test.ts` 或新增用例）：断言 `operatorSelf` 不参与 push/pull、且不会被远端覆盖。
- 老草稿里 `draft.operator` 可能是「我」，恢复后 `buildInput` 会沿用旧值（`useRecordDraft.ts:74`）。建议 `useRecordDraft.ts:74` 改成「草稿 operator 不在当前 `operators` 里就用 `operators[0]`」：
  ```ts
  operator: operators.includes(saved.operator) ? saved.operator : (operators[0] || '我')
  ```
  否则改了编号后，草稿恢复的头一单还会记成旧名字。

### 诉求 7 · 顶部是否应该固定

**现状**：见诉求 3。`sticky` 已写但失效；底部导航是 `position: fixed`（GlassKit `.glass-tab-bar-dock`，`bottom: 16px + safe-area`），一直是固定的。

**结论：应该固定，而且必须固定。** 三条理由：

1. **返回键是硬件返回键的替代品**。安卓有系统返回，iOS PWA 全屏后**没有**——顶栏返回是唯一出口。它滚走 = 用户被困在页面里。
2. **标题承载「我在哪」**。开单页 `record-top` 右下的 `stepText` 是「本场第 N 单」（`RecordEditor.tsx:167`），这是摊主唯一能确认「刚才那单记上了」的廉价信号。
3. **顶部固定不占额外的垂直空间**。它本来就在文档流里占位，`sticky` 只是在滚动时把它留在原地，净成本 0。真正的成本在**实现方式**：用 `sticky` 还是用 flex/grid 固定行（见第二节 C）。

**建议改法**：短期用诉求 3 的一行 `overflow-x: clip` 让 `sticky` 复活；中期按第二节 C 改成网格固定行，删掉 `sticky`。
**不建议**：`position: fixed` + 给 `.app-main` 加 `padding-top` 的做法。要硬编码顶栏高度（还随 safe-area 变），是 bug 温床。

**涉及文件**：同诉求 3。

**风险**：低。

## 二、三个关键判断

### A. 「删除」与「作废」的语义取舍

#### A.1 三个函数的真实语义（已逐个核实）

| 函数 | 位置 | 写什么 | 入队 | 硬约束 | 另一台手机看到 |
|---|---|---|---|---|---|
| `voidOrder(id)` | `repo.ts:925-936` | `orders.put({...o, voided:true, updatedAt})` | `{kind:'order', recordId:id}`（upsert） | **无**（任何场次都能作废） | 该单 `voided=true`，报表不计、库存加回 |
| `restoreOrder(id)` | `repo.ts:939-952` | 删掉 `voided` 字段后 `put` | `{kind:'order', recordId:id}`（upsert） | 无 | 恢复计入 |
| `deleteRecord(id)` | `repo.ts:577-596` | 物理删除 `orders` 行 + 该单全部 `lines` | `order op:'delete'` + 每条 line `op:'delete'`（墓碑） | **必须 `session.status === 'open'`，否则抛 `SESSION_CLOSED('这一场已结账，不能删除')`** | 墓碑同步 → 另一台也物理删除 |
| `undoPatchedRecord(id)` | `repo.ts:599-629` | 物理删除 + `patchedCount - 1` + 重算快照 | 同上 + `{kind:'session'}` | 场次已结账专供；未结账则转调 `deleteRecord` | 同上 |

两条额外事实：

1. **硬删除确实会同步到另一台**（墓碑 `op:'delete'` 走 outbox），所以「绕过审计、两机不一致」这个担心在同步层面**不成立**。
2. 但 **`deleteRecord` 在历史列表里基本用不了**：历史页跨所有场次，只有「当前正在记的那一场」是 `open`，其余全 `closed` → 点「删除」必抛错。这就是为什么现在只能用 `voidOrder`。
3. `deleteRecord` **不做 `patchedCount` 回退**，对补记单直接删会让报表的「补记 N 笔」永远多一笔（`undoPatchedRecord` 存在的唯一理由）。

#### A.2 结论：**不新增「真删除」，采用「表面删除 / 底层作废」**

你的倾向是对的，而且在当前数据模型下是**唯一低成本正确解**。理由按权重排序：

1. **审计与对账**：摊主每天要拿「本场金额」对现金。作废单留在列表里（灰显+划掉）是唯一能解释「为什么现金比刚才少了 80 元」的证据。真删掉之后，两台手机对不上账时**没有任何线索可查**。
2. **技术成本**：真删除需要先解掉 `deleteRecord` 的 `SESSION_CLOSED` 限制，再补 `patchedCount` 回退、再补快照重算路径 —— 那是把 `deleteRecord` 重写成 `voidOrder` 的另一个名字。
3. **同步时机的确有个真坑**（这点你的担心部分成立，但不是「状态不一致」而是「**不可撤销**」）：墓碑会立刻推给另一台手机。如果摊主在 A 手机上「删除」并已同步，B 手机的用户看不到任何痕迹，**且 A 手机上的「撤销」也救不回来**——因为撤销要把行重新 `put` 回去，但已经物理删了，本地得有完整快照才能重建（`updateRecord` 只对 open 场次可用）。作废方案下「撤销」永远是 `PUT` 一条 `voided=false`，幂等、可反复。

#### A.3 实现要点（可直接照做，只改 `HistoryPage.tsx`）

**文案映射表**（必须四处同时改，缺一处就割裂）

| 行号 | 现在 | 改成 |
|---|---|---|
| `:114` 徽标 | `已作废` | `已删除` |
| `:142` 弹层副标题 | ` · 已作废` | ` · 已删除` |
| `:161` 底部按钮（已删态） | `撤销作废` | `撤销删除` |
| `:171` 底部按钮（正常态） | `整单作废` | `删除这笔` |
| `:217` 确认框标题 | `整单作废？` | `删除这笔？` |

- `:124` 金额已有 `line-through`，**补上层级**：给 `<li>` 加 `className={o.voided ? 'is-voided' : ''}`，CSS：

  ```
  （只压透明度到 .55 不够——强光下看不清划掉；必须同时有 `line-through`。）

**把「撤销」前移到列表行**（这是体验上最关键的一步）
现状撤销必须：点进弹层 → 看到「撤销作废」→ 点。对「刚删错」的场景太深。改法：
- 在 `doVoid()` 成功后（`:64`）不再只 `onDone('已删除')`，而是：

  ```

**坑（逐条给规避）**

1. **嵌套弹层**：`voidConfirm`（`:215`）开在详情 `Sheet`（`:140`）之上。滚动锁的嵌套问题基线 M1（`kit.tsx:230` 引用计数）已修，**不要重开**。但注意：删完之后 `setOpenId(null)` 与 `setVoidConfirm(false)` 是两个 setState，`Sheet` 关闭有 260ms 动画（`kit.tsx:223`），会出现「两个 Sheet 同时播退出动画」。现状已如此，改文案时**别顺手改成只关一个**，否则确认框会留在已关闭的详情层上面。
2. **空态回声**：删完最后一单后 `grouped.length === 0` → 整页变 `Empty`（`:77`），Toast 还浮着，用户会以为「全删了」。建议 Empty 文案改为「这一场还没有记录」类，别用「还没有销售记录」这种像被清库的说法。
3. **搜索/筛选**（若第三节建议的筛选做了）：删除后条目仍应留在当前筛选结果里（灰显），不要过滤掉——否则「删掉就消失」和「真删除」在感知上没差别，撤销按钮就找不到了。
4. **报表口径**：`calc.ts` 只统计 `!voided`（`calc.ts:206`），作废即生效，无需改计算。但 `ReportPage` 若要显示「含删除」的口径，是另一个需求，**本次不做**。

#### A.4 什么前提下才允许「真删除」

若将来一定要真删，必须先满足下列**全部**条件，缺一不可：

1. 单笔、且 `session.status === 'open'`（当天、未结账）——这是 `deleteRecord` 现有的唯一安全区；
2. 该单**未同步**（`sync.pending` 里不含这条，或 `outbox` 里没有它的记录）——否则另一台手机的状态无法回退；
3. 该单**不是补记**（`session.patchedCount` 不涉及），否则要先回退计数；
4. 操作入口**不在历史列表**，而在开单成功后的 6 秒 Toast / 编辑页的「放弃这一单」——这两个位置语义清晰、误触概率低、且用户刚创建、记忆新鲜。

结论：**在摊位场景下不要做**。第 2 条（未同步）用户根本无法自行判断，等于把内部状态泄漏成 UI 逻辑。

### B. 输入法自动弹出：精确定位与改法

**定位结论：是 `autoFocus` + `Sheet` 首控件聚焦，两处叠加，不是 `defaultValue` + `focus()` 那种写法。**

排查记录（逐个排除）：

| 候选 | 位置 | 结论 |
|---|---|---|
| `autoFocus` 属性 | `ProductPicker.tsx:63` | ✅ **命中**。React 把 `autoFocus` 编译成挂载后 `node.focus()` |
| 弹层打开时 `input.focus()` | `kit.tsx:329-330` | ✅ **命中**。`Sheet` 的焦点陷阱初始化里 `(first ?? panelRef.current)?.focus()`，`ProductPicker` 的 `first` 就是搜索框 |
| `defaultValue` + 手动 focus | 全仓搜索 | ❌ 金额输入是受控 `value`（`RecordLineCard.tsx:115`），没有 `defaultValue` |
| 提交校验后聚焦金额框 | `useRecordDraft.ts:229` `amountRefs.current[bad]?.focus()` | ⚠️ 存在但**不是**根因：只在点「保存」校验失败时触发。**但这是另一个问题**——见第三节第 6 条（校验失败时自动弹键盘并滚走） |
| 连续开单后聚焦「添加商品」 | `RecordEditor.tsx:130` `addBtnRef.current?.focus()` | ❌ 是 `<button>`，不弹键盘 |

**为什么两个都要改**：单独删 `autoFocus`，`Sheet` 仍会把焦点给搜索框（`:329` 的 `first`）；单独改 `Sheet` 的默认行为，`autoFocus` 仍会立刻抢回焦点。**必须成对修改**。

**改法（精确到行）**

1. `src/ui/ProductPicker.tsx:63`：删除 `autoFocus` 这一行。
2. `src/ui/kit.tsx:272`：`Sheet` props 增加 `initialFocus?: 'first' | 'panel'`。
3. `src/ui/kit.tsx:327-330`：
   ```tsx
   const items = focusable();
   const target =
     initialFocus === 'panel'
       ? panelRef.current
       : (items.find((el) => !el.classList.contains('glass-sheet__close')) ?? items[0] ?? panelRef.current);
   target?.focus({ preventScroll: true });
   ```
   —— 注意 `initialFocus` 被包在 `useEffect(..., [])` 里（`:362` 已有 `eslint-disable exhaustive-deps`），挂载期常量，不会过期。
4. `src/ui/ProductPicker.tsx:43-46`：`<Sheet title="选商品" ... initialFocus="panel">`。
5. **验证**：安卓 Chrome + iOS Safari 各测一次「点添加商品 → 弹层升起 → 屏幕不升起键盘 → 点搜索框 → 键盘升起」。

**副作用与取舍**：焦点落在 `.glass-sheet`（`tabIndex={-1}`）上，键盘用户的 Tab 顺序从关闭按钮开始，而不是搜索框。可接受（该页主操作是点商品按钮）。若在意，可在 `ProductPicker` 里给搜索框加一个「按 Tab 搜索」的视觉提示，或在 `initialFocus="panel"` 时把搜索框排到 DOM 第一位（改 JSX 顺序，成本更高，**不建议**）。

**顺带同类问题**：`ProductFormModal`（`kit.tsx:534-541`）的 `autoFocus` + `Sheet` 双重聚焦，会触发**两次** `focus()`（React 挂载一次 + effect 一次）。在 iOS 上偶发「键盘弹起又收起」。修法：删掉 `kit.tsx:539` 的 `autoFocus`，改为 `ProductFormModal` 传 `initialFocus="first"`（默认值，无需传）——因为它的第一个非关闭控件恰好就是商品名输入框。**一处删属性即解决**。

### C. 滚动模型（影响面最大）

#### C.1 现状结构（已被 3 处硬约束卡住）

#### C.2 目标结构（顶栏固定 + 内容区独立滚动 + 底部操作区固定）

```
div.glass-bg{overflow-x:clip}                     ← 关键：不要 hidden
 └ div.app-shell{height:100dvh; display:grid; grid-template-rows:auto auto minmax(0,1fr); overflow:hidden}
    ├ header.app-nav{position:static; z-index:40}  ← 网格第 1 行，天然固定，不需要 sticky
    ├ UpdateBar（第 2 行，可选；有则占位，无则不渲染）
    └ main.app-main{
         min-height:0;                             ← ★ 缺了它 flex/grid 子项不会收缩，列表永远不滚
         overflow-y:auto;
         overscroll-behavior:contain;
         -webkit-overflow-scrolling:touch;
       }
```

**为什么用 `grid-template-rows: auto auto minmax(0,1fr)` 而不是 `flex:1 + min-height:0`**：`auto auto 1fr` 里的 `minmax(0,1fr)` 已经把 `min-height:0` 写进轨道定义，比 flex 的 `min-height:0` 更不容易被后来者删掉；且 `UpdateBar` 的出现/消失不需要任何 JS 判断行数。

#### C.5 必须考虑的 6 条风险（逐条给规避）

**风险 1（最高）· iOS 软键盘弹出时 `100dvh` 抖动，`fixed` 底栏被键盘顶上来**

- 现象：在 `.app-main` 内部滚动容器里点输入框 → 布局视口变小 → `100dvh` 变小 → 整个 grid 重排 → 列表位置跳动；同时底部 `position:fixed` 的 `.record-actions` 在 iOS 上不会随键盘上移（iOS 的 fixed 相对布局视口），会被键盘盖住。
- 规避：
  1. **开单页（`.app-main--editor`）不锁高度**，继续用文档滚动（现状即是），并在该页保留 `padding-bottom`。即内部滚动只上列表页。
  2. 视口 meta 加 `interactive-widget=resizes-content`（`index.html:5`），让安卓 Chrome 调键盘时**收缩布局视口**（而不是只缩 visual viewport）——这样底部固定条会随之上移。
  3. 若必须全站锁高，用 `height: 100svh` 而非 `100dvh`（`svh` 取「最小视口」，键盘弹出不变），代价是地址栏展开时底部会露一点白。
  4. 对容器内输入框加 `scroll-margin-block: 120px`，让浏览器在聚焦时把输入框滚到键盘上方，而不是贴着底边。

**风险 2 · `Sheet` 的 `position: fixed` 与滚动容器冲突（**必须改，否则改完会让弹层背景能滚**）**

- 现状 `kit.tsx:249-264` 用 `body{position:fixed; top:-scrollY}` 锁滚动。一旦滚动发生在 `.app-main` 里，`window.scrollY` 恒为 0 → **锁了个寂寞**，弹层打开时背景列表能被手指带着滚（尤其 iOS 穿透）。
- 改法：把锁的对象从 `body` 换成滚动容器，保留既有的引用计数（M1 已修，**改动不能破坏 `sheetLockCount` 语义**）：
  ```tsx
  function lockBodyScroll() {
    if (++sheetLockCount !== 1) return;
    const scroller = document.querySelector<HTMLElement>('.app-main');
    sheetSavedY = scroller?.scrollTop ?? window.scrollY;
    if (scroller) { scroller.dataset.locked = '1'; sheetSavedY = scroller.scrollTop; }
    else { document.body.style.position = 'fixed'; document.body.style.top = `-${sheetSavedY}px`; }
  }
  ```
  配 CSS：
  ```css
  .app-main[data-locked='1'] { overflow: hidden; }
  ```
  解锁时 `delete dataset.locked` 并把 `scrollTop` 还原。**注意**：`overflow:hidden` 会重置 `scrollTop` 到 0 吗？不会（`hidden` 仍是可编程滚动的），所以还原是安全的；但 `display:none` 会，所以**不要**用 `display` 来锁。
- 顺带：`.glass-sheet-overlay` 是 GlassKit 的 `position:fixed; inset:0`，它不依赖祖先滚动，无需改。

**风险 3 · `position: sticky` 在 `overflow: auto` 容器内的行为差异**

- 在内部滚动容器里 `sticky; top:0` 是**正常工作**的（这正是它的设计场景）。但有三个陷阱：
  1. sticky 元素的**最近滚动祖先**必须就是 `.app-main`；任何中间层加 `overflow:hidden`（很常见的「为了圆角裁剪」）会让 sticky 再次失效。**清单**：`.page-stack`、`.glass-card`、`.day-header` 的父 div（`HistoryPage.tsx:82`）——都**不要**加 `overflow`。
  2. sticky 元素**必须有背景**且 `z-index` 大于内容，否则内容从底下透出（半透明玻璃卡尤其明显）。`.day-header` 现在没背景（`styles.css:464-472` 只有 padding），必须补。
  3. 高度为 0 的 sticky 父容器（如 `.day-header` 的父 `div`）不影响；但如果把 sticky 放在 `<li>` 上，会被 `ul` 的行高约束成「只在本组内吸顶」——这**恰好是 HistoryPage 想要的效果**（天标题在本天内吸顶），所以若想「全天吸顶」就放在 `.day-header` 上，若想「整页一个筛选条吸顶」就提到 `.page-stack` 外层。

**风险 4 · 下拉刷新被禁用 / 过度滚动链**

- `body{overscroll-behavior-y:none}`（`styles.css:32-36`）已经关掉了整页下拉刷新，这是对的（摊位不能误触刷新丢单）。
- 新的 `.app-main` 加 `overscroll-behavior-y: contain` 是**必须**的：否则列表滚到顶后继续下拉，滚动链会冒泡到 body，iOS 会出现「整页回弹 + 露出浏览器地址栏」，PWA 全屏下表现为黑边闪一下。
- **不要**给 `.app-main` 加 `overscroll-behavior: none`，那会连「滚到顶部时的橡皮筋」也关掉，手感变硬；`contain` 足够。
- 若将来想恢复下拉刷新，只能靠在 `.app-main` 的 `scrollTop === 0` 时自绘一个自定义指示器，**不建议**（成本高、误触风险大）。

**风险 5 · `prefers-reduced-motion`**

- 已有基线（`styles.css:889-909`）关掉了 `dock-in` 动画和所有 transition。新增的滚动模型要补两条：
  1. 若用 `element.scrollIntoView({behavior:'smooth'})` 做「校验失败跳到出错行」，必须在 reduce 下降级为 `behavior:'auto'`；
  2. 不要给 `.app-main` 加 `scroll-snap-type`（列表页滚动吸附在 reduce 用户/慢设备上会明显掉帧）。
- 已加进 C.3 的 CSS 片段。

**风险 6 · `position: fixed` 的底栏被意外「困住」**

- `.checkout-dock`、`.record-actions`、`.glass-toast` 都是 `position:fixed`，靠「祖先没有 `transform` / `filter` / `perspective` / `contain: paint`」才能相对视口定位。
- 现状安全：`.glass-bg` 只有 `isolation: isolate`（不创建包含块）。
- **改造红线**：给 `.app-main` 或 `.app-shell` 加 `contain: paint`（性能优化的常见冲动）、`transform: translateZ(0)`（常见于「修 iOS 闪烁」）、`will-change: transform`，都会让这三个底栏**跳到滚动容器里跟着滚**。改完必须回归验证一次。

#### C.6 HistoryPage：是否改成「只在列表区滚动 + 顶部筛选固定」

**是，但理由和你想的不完全一样。**

- 现状根本没有筛选控件（`HistoryPage.tsx` 全文无 `q` / `cat` state），只有按天分组。所谓「顶部筛选固定」= **天分组标题吸顶**。
- 报价：改成「列表区滚动 + `.day-header` sticky」的收益是**中**（销售记录不是高频页，一天开一次），但成本也是**小**（2 条 CSS）。且它是**验证滚动模型的最佳试点页**——纯列表、无输入框、无底部 dock，风险最低。
- 建议顺序：**HistoryPage 试点 → StockPage 推广 → ReportPage 表格 → 开单页不动**。

**性能提醒**：`HistoryPage` 一次渲染全部历史订单（`sorted` + `grouped` 无分页，`:31-45`）。摊位一季 2000 单时，DOM 会有 2000 个 `<li>` + 2000 个 `<ul>` 包装。内部滚动不解决这个问题（只是换了个裁切窗口）。**本次不做虚拟列表**（不引依赖），但建议先加一个「近 7 天 / 近 30 天 / 全部」的 `glass-segmented` 过滤——一条 `filter` 就能把首屏压到 100 单以内，成本 S，收益比虚拟列表高。

## 五、不建议做的（附理由）

1. **全站 `position: fixed` 顶栏 + 手动 `padding-top`**：要硬编码顶栏高度（还随 `safe-area-inset-top` 变），是「改了字号就错位」的经典 bug 源。用 grid 轨道（C.2）是零成本的正解。
2. **给 `.app-main` / `.app-shell` 加 `contain: paint` 或 `transform: translateZ(0)`「修 iOS 抖动」**：会让 `.checkout-dock` / `.record-actions` / `.glass-toast` 三个 `fixed` 元素被困进滚动容器跟着滚。抖动要用 `100svh` + `interactive-widget` 解决（C.5 风险 1）。
3. **全站虚拟列表或引入列表库**：`HistoryPage` 的真实问题是「一次渲染全部历史」，加一个时间范围过滤（S 成本）就够；摊位的单量撑不到必须虚拟化，引依赖违背项目「不引新依赖」的约束。
4. **引入 `react-router` 来支持浏览器/系统返回键**：`App.tsx` 的 `tab / sub / editor` 三态（`:32-34`）已经够用。加路由会让 PWA 的 `start_url`、`base`（`./`）、gh-pages 子路径、SW 缓存策略全部要重配，风险远大于收益。想要「返回键能退出弹层」的话，`Sheet` 已有 Esc 处理（`kit.tsx:332-339`），安卓返回键映射到 Esc 需要的是 `popstate` 拦截，属于另一个课题。
5. **真删除（`deleteRecord` 暴露给历史列表）**：见第二节 A.4，四条前提用户无法判断，等于把内部状态泄漏成 UI。
6. **把「选商品」从 `Sheet` 改成独立整页**：会多一次页面切换与页面级 Suspense fallback，且失去「弹层不关、连点加货」的现有优势（`ProductPicker.tsx:9` 的注释说明了这是刻意的）。
7. **深色/浅色跟随系统（`prefers-color-scheme`）**：摊位在强光下需要**强制浅色**；自动跟随会在日落时把界面切成深色，强光下直接看不清。手动二选一（诉求 6）是对的。
8. **给 Toast 加关闭按钮 / 长说明文案**：`Toast` 现在只在 `error` 时带关闭（`AppShell.tsx:254`），这是对的。摊主不会去点那个 ×，加了只增加误触面积。
9. **键盘快捷键 / 扫码枪输入优化**：手机上没有物理键盘，摊位不是超市收银台，投入产出为零。
10. **把 `100dvh` 全局换成 `100vh`（露白）或全换 `100svh`（地址栏展开时底部露白）**：`dvh` 在列表页是对的（跟随视口），只在「有输入框的页 + 键盘弹出」这一个场景需要例外处理（C.5 风险 1 的第 1 条）。
11. **给「删除一笔」加二次确认框**：可逆操作加确认是纯负担。四.12 已论证——要降成本，不是加。
